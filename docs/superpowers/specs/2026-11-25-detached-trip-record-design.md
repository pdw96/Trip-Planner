# 떼어 낸 기록: 여행에서 나가도 내 기록은 남게 (#103)

2026-11-25. 사용자 승인(2026-11-25). 빌더 확인(서브에이전트) 반영. 시안: https://claude.ai/artifact/HhktqP6gU5dVMXRizhAdoJ (1–7번 흐름을 사용자가 확인함).

## 1. 왜

지금은 함께하는 여행(#15)에서 나가거나 내보내지면 그 여행을 더는 볼 수 없다. 나가는 순간 내 돈 지출과 내 예산도 지워진다(#89 §5.4). 실수로 나갔다가 다시 들어와도 지운 돈 기록은 돌아오지 않는다(#103 댓글).

사용자가 말한 나가는 까닭은 **지인과 소원해져서**, 또는 **누군가에게 들키면 안 돼서**다. 그 사람들과는 연결을 끊고 싶지만, 내가 다녀온 기억(어디 갔는지, 내 일정, 내가 쓴 돈)은 내 계정에 남아서 내가 볼 수 있고 관리할 수 있어야 한다.

사용자가 정한 것:

- 모양은 "내 기록"과 "함께 가는 여행"을 **떼었다 붙였다** 하는 것이다(사용자의 말).
  - **떼기**: 나가는 순간 내 몫이 내 계정에 따로 남는다. 사용자가 누를 버튼은 없다.
  - **붙이기**: 떼었던 **그 여행**에 다시 초대받아 들어오면 내 몫이 원래 자리로 돌아간다.
  - 따로 만든 내 여행을 남의 여행에 합치는 것은 이번 범위가 아니다(#121).
- 떼어 낸 동안 고칠 수 있는 것은 **내 몫만**이다(선택지 1). 나만 일정, 내 돈, 내 예산은 고치고, 함께 가져온 사본(모두 일정, 장소, 모임 지출)은 보기만 한다.
- 만드는 방식은 **A**다. 떼어 낸 기록을 내 계정의 여행 하나로 만든다(§4).
- 떼어 낸 기록에 함께 간 사람을 **계정 번호와 함께** 남긴다. 나중에 "내 기록" 모아 보기 화면(#122)에서 여러 여행에 걸쳐 같은 사람을 한 명으로 세기 위해서다. 사용자는 보안을 걱정했고, §5.2 와 §5.9 의 조건으로 정했다.
- 모든 여행을 모아 보는 "내 기록" 화면은 따로 한다(#122).
- 개념(승인 직전 사용자 말): **내 것은 내 여행이 원본이고 함께 가는 여행에는 사본, 모두의 것은 함께 가는 여행이 원본이고 내 여행에는 사본.** 함께 있는 동안은 원본과 사본이 같으므로 사본을 늘 맞춰 두지 않고, 나가는 순간에 만든다(이 설계). 함께 있는 동안 "내 여행"을 목록에 따로 보이지 않아도 된다(사용자). 예산 방식(모두·각자·둘 다)을 이 개념으로 넓히는 것은 다음 방향으로 남긴다.
- 떼어 낸 동안 남은 사람이 예산 통화를 바꿔 내 금액과 맞지 않게 되면, 다시 참여는 되지만 기록은 붙지 않고 따로 남는다. 초대 화면에서 미리 알린다(빌더 확인 뒤 사용자 결정, §5.4).

## 2. 목표 · 비목표 · 반목표

- 목표
  - 함께하는 사람이 나가거나, 내보내지거나, 주인이 여행을 지우면, 그 사람의 몫이 그 사람 계정의 **떼어 낸 기록**으로 저절로 남는다.
  - 떼어 낸 기록에는 그때까지의 모두 일정, 장소, 숙소(기준점), 예산 설정, 모임 지출이 **사본**으로 들어가 어디 갔는지 볼 수 있다. 사본은 보기만 한다.
  - 떼어 낸 기록 안에서 나만 일정, 내 돈 지출, 내 예산은 고치고, 지우고, 더할 수 있다.
  - 떼어 낸 기록은 통째로 지울 수 있다.
  - 남은 사람에게서는 나간 사람의 몫이 사라진다. 지금의 "나간 사람" 이름표로 남지 않는다.
  - 떼었던 그 여행에 초대 링크로 다시 참여하면 내 몫이 원래 여행으로 돌아가고 기록은 없어진다. 떼어 낸 동안 고친 내 몫은 고친 그대로 돌아간다.
  - 떼어 낸 기록에 그때 함께한 사람(주인 포함, 나 제외)을 계정 번호로 남기고, 화면에는 그 사람들의 이름을 보인다.
- 비목표
  - 따로 만든 여행을 함께 가는 여행에 합치기(#121).
  - 여행을 가로질러 모아 보는 "내 기록" 화면(#122).
  - 떼어 낸 기록을 원래가 아닌 다른 여행에 붙이기.
  - 떼어 낸 기록을 함께 쓰기(초대, 함께하는 사람). 기록은 언제나 혼자 것이다.
  - 이 기능 전에 나간 사람의 기록을 되살리기. 지워진 돈 기록은 남아 있지 않다. 프로덕션에는 나간 사람의 나만 일정도 남아 있지 않다(2026-11-25 확인, 0행).
  - 주인이 스스로 기록을 떼기. 주인은 나갈 수 없고 여행 자체가 주인 것이다.
- 반목표 (돌아가도 실패인 것)
  - 남은 사람의 데이터가 떼기나 붙이기 때문에 사라지거나 바뀐다. 예외는 §5.3 의 "나간 사람 나만 일정에 붙은 남의 금액을 일정 없는 지출로 바꾸기" 하나다(지금 일정 지우기와 같은 처리).
  - 떼어 낸 뒤에도 남은 사람이 나간 사람의 몫을 보거나, 나간 사람이 남은 사람이 그 뒤에 바꾼 것을 본다.
  - 떼어 낸 기록 안의 사본을 어떤 경로로든(화면이 아니라 요청을 직접 보내도) 고칠 수 있다.
  - 남의 기록에 내 몫을 붙이거나, 내 몫을 남의 여행으로 옮기는 요청이 통한다(id 를 섞어 보내도).
  - 떼기가 중간에 멈춰 멤버 행은 지워졌는데 기록은 없거나, 기록이 반만 생긴다.
  - #89 보안 규칙이 깨진다(남의 내 돈이 어떤 경로로든 보임). 떼어 낸 기록에 남의 내 돈이 들어가는 것도 포함한다.
  - 함께 간 사람의 계정 번호가 브라우저로 나간다.
  - 지금 여행(나간 사람이 없는 여행)의 화면이나 동작이 바뀐다.

## 3. 제약

- 마이그레이션 PR(`CLAUDE.md` '마이그레이션 PR'): 자동 머지 없음. 사람이 SQL 을 보고 `human-approved` 를 붙이면 `npm run db:migrate`(실행 직전 사람 확인), 그다음 자동 머지. 위험 경로는 `src/db/schema.ts`, `drizzle/**`. 새 의존성은 없다.
- 소유권 코드(여행·일정·장소·예산 쓰기 조건, 나가기, 참여)를 건드리므로 `/security-review` 대상이다.
- 여행 접근은 `accessibleTrips(userId)`, 주인만 하는 일은 `ownedTrips(userId)`. 하위 쿼리는 하위 id, 여행 id, 접근 조건을 한 SQL 문에 묶는다(`docs/status.md` '쿼리 구조').
- 여러 테이블을 한 번에 바꾸는 동작은 원자적이어야 한다. 지금까지처럼 데이터를 바꾸는 CTE 한 문으로 한다(§6).
- 이 세션의 DB 는 프로덕션뿐이다(`DATABASE_URL`). Neon MCP 는 읽기 전용이다. SQL 은 PGlite 로, 화면은 임시 테스트 계정으로 확인한다(§5.10).
- 상한: 장소 100(`MAX_PLACES_PER_TRIP`), 지출 행 300(`MAX_BUDGET_ITEMS_PER_TRIP`), 함께하는 사람 20(`MAX_MEMBERS_PER_TRIP`).
- 단위 시험 대상 순수 모듈(`src/lib/*.ts`)은 다른 모듈을 import 하지 않는다. DB 시험은 없다.
- 사용자에게 보이는 문구는 한국어다.

## 4. 방법 (사용자가 A 를 고름)

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| **A** | **떼어 낸 기록 = 나가는 사람이 주인인 새 여행.** 모두의 것은 복사, 내 몫은 옮김 | 지금 여행 화면과 쿼리를 거의 그대로 쓴다. 남은 사람이 무엇을 하든(여행 삭제 포함) 기록이 바뀌지 않는다 | 쓰기 쿼리마다 "기록이면 내 것만" 조건이 빠짐없이 들어가야 한다. 붙일 때 사본 일정에 붙은 내 돈을 원래 일정에 다시 이어야 한다 |
| B | 내 몫은 원래 여행에 두고 모두의 것 사본만 따로 저장(JSON 등) | 붙이기가 쉽다(옮긴 것이 없음) | 남은 사람이 모두 일정을 지우면 거기 붙은 내 돈이 cascade 로 지워지고, 주인이 여행을 지우면 내 몫도 다 지워진다. "연결을 끊는다"는 목적을 지키지 못한다. 사본을 보일 화면도 새로 만들어야 한다 |
| C | 나간 뒤에도 원래 여행을 읽기 전용으로 계속 보기 | 복사가 없다 | 남은 사람의 변경이 계속 보이고, 지우면 같이 사라진다. 목적과 반대라 일찍 뺐다 |

## 5. 설계

### 5.1 개념

- **기록 여행**: `trips.detached_at IS NOT NULL` 인 여행. 주인(`trips.user_id`)은 나간 사람이다. `detached_from_trip_id` 는 원래 여행을 가리키고, 원래 여행이 지워지면 null 이 된다(그러면 다시 붙을 곳이 없다).
- **내 몫** (사람 P 기준, 여행 T 안에서)
  - P 의 나만 일정: `schedule_items.for_user_id = P`. 누가 만들었든 P 의 것이다(#90 에서는 남이 P 의 일정을 만들 수 있다).
  - P 의 내 돈 지출: `budget_items.owner_user_id = P`.
  - P 의 내 예산: `trip_personal_budgets (T, P)`.
- **모두의 것**: 여행 정보(제목·목적지·날짜·메모·나라), 장소, 기준점, 예산 설정(`trip_budgets`), 모두 일정(`for_user_id IS NULL`), 모임 지출(`owner_user_id IS NULL`).
- **남의 것**: 다른 사람의 나만 일정과 내 돈. 기록에 넣지 않는다. 남의 내 돈은 P 가 원래 볼 수 없었다. 남의 나만 일정은 P 가 볼 수 있었지만, 그 사람만의 계획이라 넣지 않는다. (내 판단)

### 5.2 DB (마이그레이션, 파괴적 아님)

- `trips`
  - `detached_from_trip_id uuid NULL REFERENCES trips(id) ON DELETE SET NULL`
  - `detached_at timestamptz NULL`
  - 검사 제약: `detached_from_trip_id IS NULL OR detached_at IS NOT NULL`.
  - 부분 색인 `(user_id, detached_from_trip_id) WHERE detached_from_trip_id IS NOT NULL`(고유 아님). 한 사람이 같은 여행에서 떼어 낸 기록이 **여럿일 수 있다**. 통화가 맞지 않아 붙지 않은 기록(§5.4)이 남은 채 다시 나가거나, 옛 배포로 되돌린 동안 붙이기 없이 다시 참여한 뒤 새 코드에서 나가는 경우다. 고유로 두면 이때 나가기·내보내기·여행 지우기가 묶음째 실패한다. (빌더 확인 뒤 내 판단)
  - `detached_from_trip_id` 하나만의 색인은 없다(위 색인은 `user_id` 가 앞이다). 그래서 여행을 지울 때 `ON DELETE SET NULL` 이 그 여행을 가리키는 기록을 찾으려고 `trips` 를 훑는다. 지금 크기에서는 무시할 만하다. 느려지면 색인을 더하는 마이그레이션을 따로 낸다. (최종 리뷰 뒤 내 판단)
- `schedule_items.copied_from_id uuid NULL` (FK 없음). 기록 안의 모두 일정 사본이 원래 일정 id 를 기억한다. 붙일 때 사본에 붙은 내 돈을 원래 일정에 다시 잇는 데만 쓴다. 원래 일정이 지워져도 값은 남는다(찾으면 없을 뿐).
- 새 테이블 `trip_record_companions`
  - `trip_id uuid NOT NULL REFERENCES trips(id) ON DELETE CASCADE`
  - `user_id text NOT NULL REFERENCES "user"(id) ON DELETE CASCADE`
  - `was_owner boolean NOT NULL DEFAULT false`
  - 기본 키 `(trip_id, user_id)`.
  - 이름은 저장하지 않고 화면에 보일 때 `user.name` 에서 읽는다. 그 사람이 계정을 지우면 행이 함께 지워져, 번호도 이름도 남지 않는다. 사용자에게는 "번호와 이름을 남기고 탈퇴하면 둘 다 지운다"고 말했는데, 이 모양이 그 뜻을 더 단순하게 지킨다. 탈퇴한 사람은 "탈퇴한 사람"으로 보이지 않고 목록에서 빠진다. (내 판단)
- Better Auth 테이블은 바꾸지 않는다.

**옛 코드와 새 DB** (`CLAUDE.md` '마이그레이션 PR'):

1. 적용부터 새 배포 READY 까지: 비어도 되는 칸 셋, 새 테이블 하나, 기존 행에 영향 없는 제약·색인이다. 옛 코드는 새 칸을 모르고 지나치고, 이때는 기록 여행이 아직 없다. **안전.**
2. 그 뒤 옛 배포로 되돌릴 때(Instant Rollback): 옛 코드는 기록 여행을 그 사람의 보통 여행으로 본다.
   - 기록 안의 사본을 고칠 수 있게 되고, 기록에 초대 링크를 만들어 다른 사람을 들일 수 있다. 그러면 T 에 없던 사람(Q)도 T 의 모두 일정·장소·모임 지출의 사본을 보게 된다. 이것은 P 가 원래 볼 수 있던 데이터를 P 가 골라서 보여 주는 것이다(지금도 P 는 그 내용을 화면을 찍거나 옮겨 적어 나눌 수 있다). P 가 볼 수 없던 것(남의 내 돈, 남의 나만 일정)은 기록에 없으므로 드러나지 않는다.
   - 옛 코드로 나가면 지금처럼 내 돈과 내 예산이 지워진다(지금 동작).
   - 옛 코드로 다시 참여하면 붙이기 없이 멤버가 된다. 새 코드로 돌아오면 그 사람은 멤버이면서 기록도 가진다. 기록은 그대로 보이고, 다음에 나가면 기록이 하나 더 생긴다(색인이 고유가 아니므로 막히지 않음).
   - 판정: 보안 우회나 남의 데이터 손상이 아니다. 롤백 금지선을 두지 않는다.
   - 다시 새 코드로 오면 기록에 멤버가 있을 수 있다. 새 코드는 기록 여행에서 함께하는 사람 칸을 숨기고 참여·초대를 막을 뿐, 남은 멤버 행을 지우지는 않는다. 그 멤버는 보통 멤버처럼 사본을 볼 수 있다. 모두 일정·모임 지출·장소 같은 공유 쓰기는 §5.5 조건에 막히지만, 자기 몫인 나만 일정·내 돈은 쓸 수 있다(`forUserAllowed`·`sideWritable` 이 본인 행을 허용). 그 행은 주인이 기록을 지우면 함께 지워진다. 롤백 경우에만 생기는, 받아들인 동작이다.
     - 멤버가 남은 기록은 붙이지 않는다(§5.4). 붙이면 기록을 지울 때 그 멤버의 멤버 행과 그 멤버가 둔 행이 cascade 로 지워지기 때문이다. 초대 화면의 안내도 이 기록은 세지 않아 아무 말도 하지 않는다. 기록은 그대로 기록으로 남고, P 가 보고 지울 수 있다.
     - 남은 멤버는 화면으로 나갈 수 없다(기록에서는 함께하는 사람 칸 `MembersSection` 을 숨긴다). P 가 기록을 지우면 함께 빠진다.
     - 드문 롤백 경우라 받아들인다. 롤백 금지선을 두지 않는다는 판정은 그대로다.

### 5.3 떼기

**언제**: 함께하는 사람 P 에 대해 다음 세 가지 때 떼어 낸다.
- `leaveTrip`: P 가 스스로 나감.
- `removeMember`: 주인이 P 를 내보냄.
- `deleteTrip`: 주인이 여행을 지움. 그때의 멤버마다 떼어 낸다(최대 20명). 주인 몫은 떼지 않는다(주인이 지우기로 한 여행이다).

**무엇을** (여행 T, 사람 P, 새 기록 R). 한 묶음으로 원자적으로 한다. 묶음의 모든 문은 "P 가 지금 T 의 멤버이고, 요청한 사람이 그럴 자격이 있음"(스스로 나감이면 본인, 내보냄·지움이면 T 의 주인)을 조건으로 건다. 조건이 맞지 않으면 아무것도 바뀌지 않는다.

1. R 을 만든다. T 의 제목·목적지·날짜·메모·나라를 복사하고, `user_id = P`, `detached_from_trip_id = T`, `detached_at = now()`, 초대 칸은 비운다.
2. 함께한 사람을 적는다. T 의 주인(`was_owner = true`)과 P 를 뺀 멤버를 `trip_record_companions` 에 넣는다.
3. T 의 장소를 모두 R 로 복사한다. 좌표와 `coords_fetched_at` 도 그대로 복사한다. 모두 일정이 가리키는 장소만이 아니라 모두다. 지도는 장소 목록을 그리기 때문이다. (내 판단)
4. T 의 기준점을 R 로 복사한다. 장소 id 는 `google_place_id` 로 R 의 사본에 맞춘다(여행마다 고유하다).
5. T 의 예산 설정(`trip_budgets`)이 있으면 R 로 복사한다.
6. T 의 모두 일정을 R 로 복사한다. `copied_from_id` 에 원래 id 를 적고, 장소 id 는 4번처럼 맞춘다. 순서(`position`)와 끝냄(`done`)도 복사한다.
7. P 의 나만 일정을 R 로 **옮긴다**(`trip_id = R`, 장소 id 를 R 의 사본으로). 옮기기 전에, 그 일정에 붙은 남의 금액(모임 지출, 다른 사람의 내 돈)은 T 에 남긴다. 일정 연결을 끊고 일정 제목·날짜를 이름·날짜로 가진 "일정 밖 지출"로 바꾼다. 지금 `deleteScheduleItem` 의 `moved` 와 같은 처리다. 모임 지출이면 6번처럼 R 에도 사본을 둔다(9번).
8. P 의 내 돈 지출을 R 로 **옮긴다**.
   - 모두 일정에 붙은 것은 R 의 그 일정 사본(`copied_from_id` 로 찾음)에 다시 잇는다.
   - P 의 나만 일정에 붙은 것은 그 일정과 함께 간다.
   - 남의 나만 일정에 붙은 것은 R 에 그 일정이 없으므로 일정 밖 지출로 바꾼다(제목·날짜는 그 일정에서). 다시 붙을 때도 그 일정에 다시 잇지 않고 일정 밖 지출로 돌아간다. 다시 이으려면 원래 일정 id 칸이 더 필요한데, 남의 일정에 내 돈을 적는 일이 드물어 두지 않는다. (빌더 확인 뒤 내 판단)
   - 일정 밖 지출은 그대로 옮긴다.
9. T 의 모임 지출을 R 로 복사한다. 모두 일정에 붙은 것은 사본 일정에 잇고, 남의 나만 일정에 붙은 것은 일정 밖 지출로 복사한다.
10. P 의 내 예산을 R 로 옮긴다.
11. P 의 멤버 행을 지운다.

지금 `removeMemberAndPrivateRows` 가 하던 "내 돈과 내 예산 지우기"는 없어진다. 8번과 10번의 옮기기가 그 자리를 대신한다.

상한: R 은 T 의 부분집합을 담으므로 장소와 지출 행 상한을 넘지 않는다. 7번에서 T 에 일정 밖 지출이 늘어도 행 수는 그대로다(바꾸기일 뿐).

### 5.4 붙이기

**언제**: P 가 초대 링크로 T 에 참여하고(`joinTrip`), P 에게 `detached_from_trip_id = T` 인 기록이 있을 때. 기록이 여럿이면(§5.2) 참여 한 번에 **하나만** 붙인다. 붙을 수 있는 것(남은 멤버가 없고 통화가 맞는 것) 가운데 가장 최근에 떼어 낸 것이다. 더 오래된 것은 기록으로 남아 보고 지울 수 있다. 여럿을 한 문에서 붙이면 두 기록의 내 돈이 같은 원래 일정으로 다시 이어지거나(일정·사람마다 고유 색인 `budget_items_schedule_owner_idx`) 내 예산 둘이 함께 T 로 가(`trip_personal_budgets` 기본 키) 고유 충돌로 참여 전체가 실패할 수 있어서다. 다시 나가면 새 기록이 가장 최근이 되므로, 오래된 기록은 더 새 기록을 지우거나 그것이 통화 때문에 붙지 못할 때만 붙는다. 여럿을 합쳐 붙이는 것은 하지 않는다. (최종 리뷰 뒤 내 판단) 참여와 같은 원자적 묶음에서 한다. 붙이기의 모든 문은 "P 가 이제 T 의 멤버이고 R 의 주인"을 조건으로 건다. 참여가 실패하면(상한, 틀린 링크) 아무것도 바뀌지 않는다.

**통화가 맞지 않으면 붙이지 않는다** (사용자 결정, 선택지 1). 떼어 낸 뒤에는 P 의 금액이 T 에 없으므로, 남은 사람이 T 의 예산 통화나 현지 통화를 바꿀 수 있다(`upsertTripBudget` 의 통화 잠금이 P 의 행을 더는 보지 않음). 그대로 옮기면 "금액의 통화는 그 여행의 예산·현지 통화" 규칙이 깨지고 합계가 조용히 틀어진다.
- 기록 R 마다 판정한다. R 의 P 내 돈 행 가운데 하나라도 예상 통화나 실제 통화가 T 의 지금 예산 통화·현지 통화 어느 쪽도 아니면(T 에 예산 설정이 없는데 금액 행이 있는 경우도 포함) R 은 붙이지 않는다. 일부만 붙이지 않는다(R 통째로 붙거나 남는다).
- 붙지 않은 R 은 그대로 기록으로 남고, 참여는 된다. P 는 T 에 내 몫 없이 들어간다.
- 내 예산(`trip_personal_budgets`)의 통화는 판정에 넣지 않는다. 지금 "낡은 내 예산" 처리가 맡는다(3번).

1. R 의 P 나만 일정(R 에서 `for_user_id = P` 인 것. 떼어 낸 동안 새로 만든 것도 포함)을 T 로 옮긴다.
   - 장소 id 는 `google_place_id` 로 T 의 장소에 맞춘다. T 에 그 장소가 없으면 장소 id 를 비우고, 일정의 글자 장소(`place`)에 그 장소 이름을 남긴다. (내 판단, §6)
   - 순서: 옮긴 일정이 들어간 T 의 날마다 지금 일정 저장 뒤처럼 그날 순서를 다시 맞춘다(`settleDayOrder` 와 같은 규칙: 시각 있는 일정끼리는 시각 순, #41). 시스템 동작이다. (빌더 확인 뒤 내 판단)
2. R 의 P 내 돈 지출을 T 로 옮긴다.
   - 사본 일정에 붙은 것은 `copied_from_id` 의 원래 일정이 T 에 있으면 거기에 잇는다. 없으면(남은 사람이 그 사이에 지웠으면) 일정 밖 지출로 바꾼다(시안 7번).
   - P 의 나만 일정에 붙은 것은 그 일정과 함께 간다.
   - 일정 밖 지출은 그대로 옮긴다.
   - T 의 지출 행이 상한(300)을 조금 넘을 수 있다. 붙이기를 막지 않고 받아들인다. 그 뒤 새로 넣기만 막힌다. (내 판단)
3. R 의 P 내 예산을 T 로 옮긴다. 예산 통화가 그 사이 바뀌었으면, 지금 있는 "낡은 내 예산" 처리(`trip_personal_budgets.currency`)가 그대로 맡는다.
4. R 을 지운다. 사본과 함께한 사람 행은 cascade 로 지워진다.

**초대 화면**: P 에게 이 여행에서 떼어 낸 기록이 있으면 안내를 보인다. 고르는 버튼은 따로 없다. 참여하면 붙는다.
- 붙을 수 있으면: "전에 이 여행에서 떼어 낸 기록이 있어요. 참여하면 내 일정과 내 돈이 원래 자리로 돌아가고, 떼어 낸 기록은 목록에서 없어져요."(시안 6번)
- 통화가 맞지 않으면: "전에 이 여행에서 떼어 낸 기록이 있어요. 그 사이 예산 통화가 바뀌어 기록은 다시 붙지 않고 내 여행 목록에 따로 남아요."
- 둘 다 있으면(기록이 여럿) 둘을 함께 보인다: 붙는 문구 뒤에 "통화가 바뀐 기록은 따로 남아요." 붙을 수 있는 기록이 여럿이어도 문구는 하나다. 그 가운데 가장 최근 것만 붙고 나머지는 기록으로 남는다(위 '언제'). 흔한 경우(붙을 기록 하나)에 "떼어 낸 기록은 목록에서 없어져요"가 맞으므로 문구는 그대로 둔다.
- 남은 멤버가 있는 기록(§5.2 롤백 경우)은 후보가 아니라서 안내에 넣지 않는다.
- 화면의 판정과 참여 때의 판정 사이에 통화가 바뀔 수 있다. 참여 때의 판정이 정하고, 결과가 안내와 다르면 참여 뒤 화면(여행 화면)에서 알 수 있으면 충분하다. (내 판단)

### 5.5 기록 여행 안에서 쓰기 (보안)

기록의 주인은 P 라서 `accessibleTrips(P)` 를 통과한다. 그래서 **쓰기 쿼리마다** 기록인지 확인하는 조건을 더한다. 화면에서 버튼을 숨기는 것은 편의일 뿐이고, 막는 것은 쿼리다.

- **허용**
  - P 의 나만 일정 넣기·고치기·지우기·끝냄 표시. 기록에서는 "누구" 칸이 없고, 서버가 `for_user_id = P` 로 정한다. 고치기·지우기 대상도 `for_user_id = P` 인 일정만이다.
  - 그 일정의 장소: R 에 이미 있는 장소 고르기, 또는 글자 장소. **새 장소 검색(장소 만들기)은 막는다.** 붙일 때 새 장소를 T 에 들이는 문제를 피하려고서다. (내 판단, §6)
  - P 의 내 돈 지출 넣기·고치기·지우기. 기록에서는 "누구 돈" 고르기 없이 언제나 내 돈이다. 모두 일정 사본에 내 돈 금액을 붙이는 것도 허용한다(P 의 행이므로).
  - P 의 내 예산 정하기.
  - 기록 통째로 지우기(`deleteTrip`). 기록에는 멤버가 없으므로 떼기는 일어나지 않는다.
  - 좌표 새로 받기(`setPlaceCoords`). 사용자 쓰기가 아니라 Google 좌표 30일 규칙을 지키는 시스템 동작이다.
  - 그날 순서 쓰기(`writeDayOrder`)와 끌어 옮기기. 사본의 `position` 도 다시 쓰이지만, 순서는 내용이 아니라 이 기록에서 보이는 차례라 "사본 고치기"로 보지 않는다. 막으면 일정 저장 뒤 순서 맞추기(`settleDayOrder`)가 돌지 못해, 시각 있는 나만 일정이 시각 순에 섞이지 않고 맨 뒤에 붙는다(#41 규칙 깨짐). `position` 말고 다른 칸은 쓰지 않는다. (빌더 확인 뒤 내 판단)
- **막음**: 여행 정보 고치기, 장소 넣기·고치기·지우기, 기준점, 예산 설정(`trip_budgets`), 모두 일정의 내용(순서 말고 모든 칸) 고치기·넣기·지우기·끝냄, 모임 지출, 초대 링크 만들기·끄기, 참여.
- **구현 모양**(빌더가 다듬는다)
  - 모두의 것을 쓰는 쿼리는 여행 조건을 "접근 가능하고 기록이 아님"으로 바꾼다. 예: `trips.ts` 에 `editableTrips(userId)`(= `accessibleTrips(userId) AND trips.detached_at IS NULL`).
  - 내 몫을 쓰는 쿼리는 `accessibleTrips` 를 그대로 쓰되, 기록이면 "그 행이 P 의 것"을 함께 요구한다. 나만 일정은 `for_user_id = P`, 내 돈은 이미 `visibleToUser` 가 본인 행만 고른다. 넣기에서 서버가 정하는 값(`for_user_id`, `side`)도 기록이면 P 와 내 돈으로 고정한다.
  - `joinTrip`, `setInviteTokenHash` 는 기록 여행을 거른다(`detached_at IS NULL`).
- 바꿔야 하는 쓰기 함수를 빠짐없이 표로 정리하는 것은 구현 계획에서 한다. 지금 쓰기 함수는 `trips.ts`(updateTrip), `places.ts`(create/update/delete), `trip-bases.ts`(setTripBase), `schedule-items.ts`(일정 쓰기 넷과 그 분기 여섯, writeDayOrder, setScheduleItemDone, deleteScheduleItem), `budget.ts`(upsertTripBudget, setPersonalBudget, setScheduleItemAmounts, setScheduleItemActual, create/update/deleteExtraItem), `trip-members.ts`(초대·참여) 다.

### 5.6 남은 사람

- 떼기의 7번과 8번으로 P 의 몫은 T 에서 빠진다. 남은 사람에게 "나간 사람" 이름표로 접혀 보이던 일은 이제 생기지 않는다(시안 5번).
- 지금 있는 "나간 사람" 이름표 코드(`listScheduleForUserNames`, 고치기 양식의 "이름 (나감)")는 그대로 둔다. 이 기능 전 데이터는 0행이지만, 옛 배포로 되돌린 동안 생길 수 있다(§5.2-2). 정리는 #120 에 적는다. (내 판단)
- 나가기·내보내기 확인 창 문구를 바꾼다(시안 2번). 지금 문구가 "내 돈 기록이 지워진다"고 말하고 있다면 떼어 낸 기록으로 남는다는 안내로 바꾼다. 내보내기 창도 "그 사람의 기록은 그 사람 계정에 남는다"로 바꾼다.
- 여행 지우기 확인 창에는 "함께하는 사람들에게는 각자 기록이 남아요."를 더한다.

### 5.7 화면

- **내 여행 목록**(시안 3번): "다가오는 여행", "지난 여행" 아래에 "떼어 낸 기록" 칸을 둔다. 기록은 날짜와 관계없이 이 칸에만 보인다. 한 줄에는 제목 옆에 "B님 여행에서 · 11/20 떼어 냄" 이름표를 단다. B 는 `was_owner` 인 함께한 사람의 이름이고, 그 사람이 없으면(탈퇴) "함께한 여행에서"로 쓴다. 미니 노선은 회색이다.
- **기록 안**(시안 4번): 지금 여행 화면을 쓴다.
  - 맨 위에 안내 띠: "떼어 낸 기록 · B님의 여행에서 11월 20일에 떼어 냈어요. 함께 쓰던 일정, 장소, 모임 지출은 그날 모습 그대로 보기만 할 수 있어요."
  - 안내 띠 아래 한 줄: "B님, C님과 함께". 함께한 사람이 없으면 줄을 뺀다.
  - 숨기는 것: 함께하는 사람 칸, 초대 링크, 여행 고치기 버튼, 장소 넣기·고치기, 기준점 정하기, 예산 설정, 모두 일정과 모임 지출의 고치기·지우기·끝냄 버튼, "누구"·"누구 돈" 고르기. 끌어 옮기기는 남긴다(§5.5).
  - 모두 일정 사본의 내 돈(§5.5 허용): 예산이 있으면 사본의 제목을 눌러 내 돈만 적는 양식을 연다. 일정 칸은 없고, 모임 금액이 있으면 글자로만 보이며, 내 돈 예상·실제를 넣고 고치고 비워 저장하면 지운다. 사본의 끝냄은 바꿀 수 없으므로 체크칸에서 여는 실제 지출 칸 대신 이 양식에서 실제를 적는다. (최종 리뷰 뒤 내 판단)
  - 지도와 동선: 보는 사람이 P 이므로 지금 규칙(모두 + 나만)이 그대로 맞는다.
  - 지우기 버튼은 "기록 지우기"로 부르고 기록의 주인(P)에게 보인다. 확인 창: "이 기록을 지울까요? 지우면 되돌릴 수 없어요."
- **초대 화면**(시안 6번): §5.4.
- 함께한 사람의 계정 번호는 브라우저로 보내지 않는다. 화면 데이터에는 이름만 싣는다.

### 5.8 데이터 흐름

- 나가기: `leaveTripAction` → `leaveTrip`(떼기 묶음) → 무효화(`/trips`, `/trips/[T]`) → 지금처럼 `/trips` 로 보낸다. 목록에 기록이 보인다.
- 내보내기: `removeMemberAction` → `removeMember`(떼기 묶음) → 무효화.
- 여행 지우기: `deleteTripAction` → `deleteTrip`(멤버마다 떼기 + 여행 삭제를 한 묶음).
- 참여: `joinTripAction` → `joinTrip`(참여 + 붙이기를 한 묶음) → 무효화(`/trips`, `/trips/[T]`, 기록 R 의 경로).
- 기록 보기: `getTrip` 이 `detachedAt`, `detachedFromTripId` 를 함께 돌려주고, 화면은 이 값으로 기록 모드를 고른다. 함께한 사람 이름은 새 쿼리(예: `listRecordCompanions(userId, tripId)` → 이름과 `wasOwner` 만)로 읽는다.

### 5.9 보안 정리

- 떼기·붙이기 묶음의 모든 문은 자격 조건(§5.3·§5.4)을 SQL 안에 건다. 앱에서 먼저 확인하고 나중에 쓰는 순서에 기대지 않는다.
- 붙이기 대상은 "요청한 사람이 주인인 기록"과 "그 기록의 `detached_from_trip_id` 인 여행"뿐이다. 여행 id 나 기록 id 를 입력으로 받지 않고 초대 해시로 찾은 T 와 그 사람 id 로 찾는다.
- 기록 안 쓰기는 §5.5 조건.
- 함께한 사람의 계정 번호: 서버 안에서만 쓴다(§5.7). 번호는 열쇠가 아니다. 모든 쿼리는 로그인한 사람 기준이다. 탈퇴하면 행이 지워진다(§5.2).
- `/security-review` 로 확인할 곳: 떼기·붙이기 묶음, 기록 쓰기 조건, 참여 쿼리.

### 5.10 시험·확인

- 순수 함수로 뺄 수 있는 것(예: 목록 나누기에 기록 칸 더하기, 이름표 문구)은 `src/lib/*.test.mjs` 로 시험한다.
- 떼기·붙이기 SQL 은 DB 시험이 없으므로 마이그레이션 적용 전에 PGlite 로 실제로 돌려 확인한다(`docs/status.md` '마이그레이션 SQL 을 적용 전에 확인', #89 방식). 이 세션의 `DATABASE_URL` 은 프로덕션이고 Neon MCP 는 읽기 전용이라 쓸 수 있는 미리보기 DB 브랜치가 없다. 확인할 경우는 적어도 이렇다.
  - 나가기 뒤: 기록에 사본·내 몫이 맞게 있고, T 에는 내 몫이 없고 남의 것은 그대로다.
  - 나만 일정에 모임 지출과 남의 내 돈이 붙은 경우(§5.3-7).
  - 주인이 여행을 지울 때 멤버 둘에게 각각 기록이 생기는 경우.
  - 붙이기: 원래 일정이 남은 경우와 지워진 경우(시안 7번), 떼어 낸 동안 새로 만든 나만 일정, 장소가 T 에서 지워진 경우.
  - 붙이기: 통화가 바뀌어 붙지 않는 경우, 같은 여행의 기록이 둘인 경우.
  - 남이 보낸 요청: 남의 기록 id, 남의 여행 id 로 쓰기·붙이기가 0행인지.
- 화면: `run` 스킬, Playwright 로 시안 1–7번 흐름을 두 계정으로 확인한다. 로그인은 `docs/status.md` '로그인한 화면의 브라우저 확인' 대로 프로덕션 DB 에 임시 테스트 계정(`e2e-test-` 접두어)을 넣고 끝나면 지운다. 넣기·지우기 전 SQL 전문을 보이고 사용자 확인을 받는다. 테스트 중에 생긴 기록 여행도 함께 지운다.

## 6. 빌더에게 남긴 것

- 원자성: **데이터를 바꾸는 CTE 한 문**으로 한다. PGlite 로 적용 전에 검증할 수 있는 방식이 이것이다(`db.batch` 가 neon-http 에서 한 트랜잭션인지는 이 세션에서 확인할 길이 없다). 같은 문 안의 CTE 는 서로 넣은 행을 보지 못하므로, 사본 id 맞추기는 `RETURNING`(장소는 `id, google_place_id`, 일정은 `id, copied_from_id`)을 이어 받아 한다. 기록 id 는 JS 에서 `crypto.randomUUID()` 로 미리 만들어 넘기면 쉽다. 여행 지우기는 멤버마다 떼기와 여행 삭제를 한 문에 넣는다. 옮긴 행이 문 끝의 cascade 에 지워지지 않는지는 `deleteScheduleItem` 주석과 같은 이유로 기대되지만 PGlite 로 꼭 확인한다. 한 문이 너무 커지면 떼기 SQL 을 사람 하나 단위 함수로 만들어 여행 지우기에서는 멤버 수만큼 CTE 를 이어 붙인다.
- 동시성: 떼기와 같은 때 P 가 내 돈을 쓰는 경우, 떼기와 같은 때 남이 P 의 나만 일정을 고치는 경우. 지금 `removeMemberAndPrivateRows` 주석과 같은 수준으로 창을 분석하고 받아들일 수 있는지 적는다.
- 붙일 때 T 에 없는 장소(§5.4-1): 장소 이름을 글자 장소로 남기는 방법이 지금 `schedule_items.place` 와 `title` 쓰임새와 맞는지 확인한다. 안 맞으면 장소 id 만 비우고 PR 에 적는다.
- 기록에서 새 장소 검색을 막는 것(§5.5)이 화면에서 어색하면(예: 장소 고르기 칸이 검색과 한 칸이라 떼어 내기 어려움) 새 장소를 허용하고, 붙일 때 T 에 그 장소가 없으면 만들어 넣는(장소 상한 확인) 방향으로 바꿔도 된다. 바꾸면 PR 에 적는다.
- 쓰기 함수 표(§5.5)와 각 함수의 바꿀 조건.
- 확인 창 문구의 정확한 글(§5.6), 목록 이름표 날짜 모양.
