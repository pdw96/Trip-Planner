# 여행 목록·만들기·수정·삭제 (trips CRUD) 설계

- 날짜: 2026-11-18
- 이슈: pdw96/Trip-Planner#11
- 상태: 초안 (사용자 승인 대기)

## 1. 의도

지금 앱은 홈(`/`)에서 Google 로그인만 된다. 로그인한 사람이 자기 여행을 목록으로 보고, 만들고, 고치고, 지울 수 있게 한다. `trips` 테이블은 이미 있으므로 DB 변경 없이 화면과 Server Action 만 더한다.

이 기능은 앞으로 붙을 네 기능의 바탕이다: 날짜별 일정표(#12), 가 볼 장소(#13), 예산·지출(#14), 지인과 공유(#15). 그래서 두 가지를 미리 잡아 둔다.

1. 여행 자세히 보기(`/trips/[id]`)를 중심 화면으로 만든다. 나중에 일정·장소·예산이 이 화면 아래에 들어온다.
2. "이 사용자가 이 여행에 접근할 수 있는가" 판단을 코드 한 곳에 모은다. 지금은 "내 여행만"이지만, 공유(#15)를 넣을 때 이 한 곳만 바꾸면 되게 한다.

사용자는 본인과 지인 2명이고 한국어를 쓴다. 지금은 본인만 쓴다.

## 2. 목표 / 비목표 / 반목표

**목표**
- 로그인 뒤 바로 내 여행 목록으로 간다.
- 여행 만들기·자세히 보기·고치기·삭제.
- 입력 검증: 필수 필드, 날짜 형식, 끝 날짜 ≥ 시작 날짜. 오류는 해당 칸 옆에 한국어로 보이고, 입력한 내용은 남는다.
- 다른 사람의 여행은 보이지도, 고쳐지지도, 지워지지도 않는다.

**비목표**
- 공유·초대, 일정표·장소·예산 (각각 #15, #12, #13, #14).
- 검색·필터·페이지 나누기 (여행 수가 적다).
- `use cache` 같은 데이터 캐시. 여행 데이터는 매 요청 새로 읽는다.
- 스키마 변경.

**반목표 (동작해도 실패로 본다)**
- 남의 여행 id 로 들어갔을 때 "없음"과 다른 반응이 나와, 그 id 의 여행이 있다는 것이 드러나는 것.
- 클라이언트가 보낸 값(`userId`, 숨은 필드, bind 된 id)을 믿고 범위를 정하는 것.
- 검증 오류가 났는데 사용자가 적은 내용이 사라지는 것.
- "지난 여행" 구분이 한국 날짜와 하루 어긋나는 것.
- 영어 오류 화면이 그대로 보이는 것.

## 3. 제약

- Next.js 16 App Router, `cacheComponents: true`, `partialPrefetching: true` (`next.config.ts`). 세션(`headers()`)을 읽는 컴포넌트는 `<Suspense>` 안에 있어야 한다. 레이아웃 최상단에서 세션을 `await` 하지 않는다. 구현 전에 `node_modules/next/dist/docs/` 의 관련 문서(`02-guides/forms.md`, `01-getting-started/07-mutating-data.md`, `02-guides/authentication-with-cache-components.md`, `03-api-reference/04-functions/not-found.md`)를 읽는다.
- CLAUDE.md '규칙'·'구현 규칙' 전부. 특히:
  - 현재 사용자는 `getCurrentUser()` (`src/lib/session.ts`)로만 읽는다.
  - 사용자 데이터 쿼리는 `src/db/queries/trips.ts` 에 두고 `import "server-only"`, 첫 인자 `userId`.
  - 남의 것과 없는 것은 똑같이 `notFound()`. uuid 형식이 틀린 id 는 쿼리 전에 걸러 `null`.
  - Server Action 순서: `getCurrentUser()` → 필드별 입력 검증 → `userId` 로 범위를 좁힌 쿼리 → 무효화/이동.
  - 비로그인은 `redirect("/")`.
- `package.json` 은 위험 경로(사람 승인 필요)다. 새 의존성(zod 등)을 넣지 않고 검증은 직접 짠다. 이 PR 은 위험 경로를 건드리지 않는 것이 목표다.
- DB 의 `trips_dates_check` (`end_date >= start_date`)와 같은 규칙을 앱에서도 먼저 검사한다.
- 클라우드 세션 환경 변수에는 `DATABASE_URL` 만 있고, 이 주소는 프로덕션 DB(Neon `main`)다. Better Auth 시크릿·Google 키는 Vercel 프로덕션에만 있어 클라우드 세션과 프리뷰 배포에서는 Google 로그인을 할 수 없다. 브라우저 확인 방법은 §5.5.

## 4. 고려한 방식

사용자는 구현 방식을 Claude 에 맡겼다 ("선호 없음"). 아래는 Claude 의 판단이다.

| 방식 | 내용 | 판단 |
|---|---|---|
| **A. Server Component 페이지 + 말단 Client 폼(`useActionState`) + Server Action** | 페이지는 서버에서 그리고, 입력 양식만 Client Component. 오류와 입력값을 action 상태로 돌려받는다. | **선택.** 프로젝트 규칙(기본 Server Component, 변경은 Server Action)과 Next 16 문서의 권장 방식에 맞고, 오류가 나도 입력이 남는다. |
| B. 순수 서버 폼 + 오류는 `redirect(?error=...)` | 클라이언트 JS 없음. | 오류 때 입력이 사라지고 칸별 오류 표시가 어렵다. 반목표에 걸린다. |
| C. 클라이언트 화면 + Route Handler(fetch) | SPA 방식. | "데이터 변경은 Server Action" 규칙에 어긋난다. |

삭제 확인은 두 방식을 견줬다. (a) 작은 Client Component 가 브라우저 확인 창(`window.confirm`)을 띄운 뒤 삭제 action 을 부르는 방식, (b) 별도 확인 페이지. 사용자에게 "확인 창"으로 설명했고 화면이 하나 줄어드는 (a)를 고른다.

## 5. 정한 것

### 5.1 화면과 흐름 (사용자 승인)

| 경로 | 내용 |
|---|---|
| `/` | 로그인 화면. 로그인돼 있으면 `redirect("/trips")`. (로그인 버튼의 `callbackURL` 이 `/` 이므로 로그인 뒤 여기서 목록으로 넘어간다.) |
| `/trips` | 내 여행 목록. 위쪽에 "새 여행" 버튼과 로그아웃 버튼. |
| `/trips/new` | 새 여행 만들기. 저장하면 그 여행의 자세히 보기로 이동. |
| `/trips/[id]` | 자세히 보기. 이름·여행지·날짜·메모, "고치기"·"삭제" 버튼. 앞으로 일정·장소·예산이 아래에 붙는 중심 화면. |
| `/trips/[id]/edit` | 고치기. 만들기와 같은 양식에 기존 값이 채워진다. 저장하면 자세히 보기로 이동. |

- 비로그인으로 `/trips/**` 에 오면 `redirect("/")`.
- 로그아웃하면 홈(`/`)으로 간다.
- 삭제: 자세히 보기의 "삭제" → "정말 삭제할까요?" 확인 창 → 확인을 눌러야 지우고 `/trips` 로 이동. 취소하면 아무 일도 없다.
- 남의 여행이나 없는 여행, 형식이 틀린 id → "찾을 수 없음" 화면(한국어). 셋 다 똑같이 보인다.

목록 화면:

```
내 여행                         [+ 새 여행] [로그아웃]

다가오는 여행
  겨울 휴가
  오사카 · 12/20 – 12/23
  설 연휴
  제주 · 2027/1/5 – 1/7

지난 여행
  가을 부산
  부산 · 10/3 – 10/5
```

자세히 보기:

```
겨울 휴가                      [고치기] [삭제]
오사카 · 2026년 12월 20일 – 12월 23일
메모: 항공권 예약 완료
```

### 5.2 목록 순서 (사용자 승인)

- "다가오는 여행": 끝 날짜가 오늘 이후(오늘 포함)인 여행. 시작 날짜가 가까운 순.
- "지난 여행": 끝 날짜가 오늘보다 전인 여행. 최근에 끝난 순.
- "오늘"은 한국 날짜(`Asia/Seoul`)다. 서버는 UTC 로 돈다. 여행지 시간대와는 상관없다.
- 여행이 하나도 없으면 안내 문구와 "새 여행" 버튼을 보인다. 한 칸만 비면 그 칸은 감춘다. (Claude 판단)

### 5.3 필드와 검증 (사용자 승인, 한도는 Claude 판단)

| 필드 | 필수 | 규칙 |
|---|---|---|
| 여행 이름 `title` | 예 | 앞뒤 공백 제거 뒤 1–100자 |
| 여행지 `destination` | 예 | 앞뒤 공백 제거 뒤 1–100자 |
| 시작 날짜 `startDate` | 예 | `YYYY-MM-DD`, 실제 있는 날짜(2026-02-30 거부) |
| 끝 날짜 `endDate` | 예 | 같은 형식, 시작 날짜 이후(같은 날 허용) |
| 메모 `notes` | 아니오 | 앞뒤 공백 제거 뒤 2000자 이하, 비면 `null` |

- 오류 문구 예: "여행 이름을 입력해 주세요.", "100자 이하로 입력해 주세요.", "날짜를 올바르게 입력해 주세요.", "끝 날짜는 시작 날짜와 같거나 그 뒤여야 해요." 정확한 문구는 구현자가 다듬는다.
- 검증은 서버(Server Action)에서 한다. 날짜 칸은 `<input type="date">` 를 쓰되, 브라우저 검증에 기대지 않는다.
- DB 저장 자체가 실패하면 양식 위에 "저장하지 못했어요. 잠시 후 다시 시도해 주세요."를 보이고 입력은 남긴다.

### 5.4 코드 구조 (Claude 판단)

- `src/db/queries/trips.ts` (`import "server-only"`)
  - 모든 쿼리의 "접근 가능한 여행" 조건을 한 곳(예: 내부 함수 하나)에서 만든다. 지금은 `trips.userId = userId`. 공유(#15)는 이 조건만 바꾼다.
  - `getTrip(userId, tripId)`: uuid 형식이 틀리면 쿼리 없이 `null`. 없거나 남의 것이면 `null`. 앞으로 일정·장소·예산이 "이 여행에 접근 가능한가"를 확인할 때도 이것을 쓴다.
  - 목록, 만들기(`userId` 는 인자로만 받는다), 고치기·삭제(`id` 와 접근 조건을 함께 `where` 에 넣고, 바뀐 행이 없으면 "찾을 수 없음"으로 돌려준다).
- 검증은 순수 함수로 분리해 action 이 필드별로 꺼낸 값만 넘긴다(`FormData` 를 통째로 넘기지 않는다). 결과는 성공 시 정리된 값, 실패 시 필드별 오류 + 사용자가 적은 원래 값.
- Server Action (`src/app/trips/` 아래): 만들기·고치기·삭제. 고치기·삭제의 여행 id 는 클라이언트에서 다시 들어오는 값(bind 인자 포함)이므로 믿지 않고, 위 쿼리의 uuid 검사와 `userId` 범위로 막는다. 성공 뒤 목록 경로를 무효화하고 이동한다.
- 양식 Client Component 하나를 만들기·고치기가 같이 쓴다. 삭제 버튼 Client Component 하나. 그 밖은 Server Component.
- 세션을 읽는 부분은 `<Suspense>` 안에 둔다. `params` 를 읽는 부분도 같은 경계 안에 둔다.
- 한국어 "찾을 수 없음" 화면(`not-found.tsx`)을 둔다.
- 날짜 표시: 목록은 `월/일 – 월/일`, 올해가 아닌 날짜는 연도를 붙인다. 자세히 보기는 `YYYY년 M월 D일`.

### 5.5 로그인한 화면의 브라우저 확인 (사용자 결정)

사용자가 고른 방식: 프로덕션 DB 에 임시 테스트 계정을 만들어 확인하고, 끝나면 지운다.

- 가짜 사용자 두 명(A, B)과 각자의 `session` 행을 넣는다. 실제 사용자 행과 그 여행은 읽지도 고치지도 않는다. 테스트 사용자 id 와 이메일은 실제와 겹칠 수 없는 값으로 한다(예: id 접두어 `e2e-test-`, 이메일 도메인 `example.invalid`).
- 로컬 dev 서버에 그 세션 쿠키를 붙여 Playwright 로 A 의 목록·만들기·검증 오류·자세히 보기·고치기·삭제를 확인한다. B 의 여행 주소로 A 가 들어가면 "찾을 수 없음"이 뜨는지도 확인한다.
- 정리: 테스트 사용자 행을 지운다. `session`·`trips` 는 FK cascade 로 함께 지워진다. 지운 뒤 테스트 사용자 id 로 남은 행이 0 개인지 확인한다.
- 넣기 직전과 지우기 직전에 실행할 SQL 전문을 사용자에게 보이고 확인을 받는다.
- 쿠키 서명 방식, dev 서버를 시크릿·Google 키 없이 띄우는 방법은 구현자가 `better-auth` 소스에서 확인한다. 앱 코드나 인증 설정(`src/lib/auth.ts`)을 테스트용으로 바꾸지 않는다.

## 6. 구현자에게 맡기는 것

- 파일 이름·위치의 세부(위 구조 안에서), 레이아웃 컴포넌트를 둘지 여부.
- 화면 스타일. 지금 홈 화면의 Tailwind 스타일(둥근 버튼, zinc 계열)을 따른다.
- 오류 문구의 최종 표현.
- 고치기·삭제 action 에서 "찾을 수 없음"을 `notFound()` 로 낼지 오류 상태로 돌려줄지. 단, 남의 것과 없는 것의 반응은 같아야 한다.
- 로그아웃 뒤 `/` 로 가는 방법(`router.push("/")` 등).
