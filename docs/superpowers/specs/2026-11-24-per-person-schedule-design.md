# 사람별 일정과 내 동선 (#90)

2026-11-24. 사용자 승인 대기. 빌더 확인(서브에이전트) 반영.

## 1. 왜

함께 가는 사람마다 출발지가 다르다(예: 나는 부산, 지인은 대구). 그래서 합류 지점(예: 서울역)까지 오는 표가 다르고 금액도 다르다(사용자). 지금은 일정에 "누구 일정"이 없어서, 각자의 KTX 를 일정에 넣으면 한 줄 동선이 부산역 → 동대구역 → 서울역처럼 이상하게 이어진다(#91 이후 첫날 동선은 첫 일정에서 시작한다).

사용자가 정한 것:

- 갈라지는 때는 **첫날 오는 길과 마지막 날 돌아가는 길**이다(A). 여행 중간에 갈라지는 경우는 이번 범위의 목표가 아니다.
- 오는 길·표는 **각자 알아서** 챙긴다. 그래서 화면은 **내 동선만** 그린다(②).
- 일정마다 대상은 **모두 또는 한 사람**이다(방법 1). 같은 기차를 두 사람이 타면 각자 한 줄씩 넣는다.
- 사람별 표 금액은 그 일정에 붙고 #89 규칙(모임 통장 / 내 돈)을 그대로 따른다(#90 댓글, #89 설계 §1).

## 2. 목표 · 비목표 · 반목표

- 목표
  - 일정마다 "누구": **모두**(기본) 또는 **여행 사람 중 한 명**(주인 포함).
  - 내 동선 = **모두 일정 + 나만의 일정**만 이은 것. 지도 N일차 선·핀 번호, 일정 사이 이동 시간 줄(#37), N일차 탭 숙소 표시, 구간 이동 정보 요청이 모두 이 기준을 쓴다. 보는 사람마다 동선이 다르다.
  - 남의 일정은 내 일정표에서 숨기지 않고 **한 줄로 접어** 보여 준다(합류 때 지인 도착 시각을 알 수 있게). 동선·이동 시간에는 넣지 않는다.
  - 사람이 나가거나 내보내지면 그 사람만의 일정은 지우되, 거기 붙은 남은 금액은 일정 밖 항목으로 옮긴다.
- 비목표
  - 일정 하나에 여러 사람 고르기(사용자가 방법 1 을 고름).
  - 사람마다 다른 밤 숙소(기준점은 여행에 하나, #91 그대로).
  - 사람마다 출발지(집)를 따로 저장하기. 오는 길은 "나만" 일정으로 적는다.
  - 남의 동선 보기, 사람별 선 색.
  - 남의 일정을 남에게 숨기기(일정은 함께하는 사람 모두가 본다. 숨는 것은 #89 의 내 돈 금액뿐).
- 반목표 (돌아가도 실패인 것)
  - 지금 여행(모든 일정이 "모두")의 화면·동선·이동 시간·예산 숫자가 바뀐다.
  - 남의 "나만" 일정이 내 동선(선, 번호, 이동 시간, Google 구간 요청)에 끼어든다.
  - 여행 사람이 아닌 사용자 id 를 "누구"에 넣을 수 있다(id 를 섞어 보내도).
  - 사람이 나갈 때 모임 통장 금액이나 남의 내 돈 기록이 경고 없이 사라진다.
  - #89 보안 규칙이 깨진다(남의 내 돈이 어떤 경로로든 보임).
  - 마이그레이션이 기존 데이터를 지우거나 바꾼다.

## 3. 제약

- 마이그레이션 PR(`CLAUDE.md` '마이그레이션 PR'): 자동 머지 없음, 사람이 SQL 을 보고 `human-approved` → `npm run db:migrate`(실행 직전 사람 확인) → 자동 머지. 위험 경로 `src/db/schema.ts`, `drizzle/**`. 새 의존성 없음.
- 소유권 코드(나가기·내보내기, 쓰기 쿼리 조건)를 건드리므로 `/security-review` 대상.
- 여행 접근은 `accessibleTrips(userId)` 하나. 하위 쿼리는 하위 id·여행 id·접근 조건을 한 SQL 문에 묶는다.
- neon-http 는 트랜잭션이 없다. 여러 테이블을 함께 바꾸면 데이터를 바꾸는 CTE 한 문.
- 단위 시험 대상 순수 모듈(`src/lib/*.ts`)은 다른 모듈을 import 하지 않는다. 시험은 `src/**/*.test.mjs`, DB 시험은 없다.
- 사용자에게 보이는 문구는 한국어.

## 4. 방법 (사용자가 1 을 고름)

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| **1** | **일정에 "누구" 칸 하나** `schedule_items.for_user_id`(null = 모두) | #89 의 `budget_items.owner_user_id` 와 같은 모양. FK 로 사용자 무결성, 쿼리 조건이 "null 또는 나" 하나. 금액이 한 줄 = 한 사람이라 #89 와 맞물림 | 같은 기차를 탄 두 사람은 두 줄 |
| 2 | 대상 사람 배열 칸 | 한 줄로 여러 사람 | 배열 원소는 FK 검사 불가(나간 사람 id 가 남음). 금액 한 줄이 여러 사람 몫이 되어 나누기 문제가 다시 생김(#89 에서 피함) |
| 3 | 연결 테이블(일정 × 사람) | 여러 사람 + FK | 일정 저장마다 두 테이블 쓰기(지금도 큰 일정 저장 CTE 가 더 커짐). 나누기 문제는 2 와 같음 |

화면 쪽(사용자 결정): 첫날 화면에 ① 모두의 동선을 한꺼번에 / **② 내 동선만** 중 ②. 오는 길을 각자 챙기기 때문이다.

## 5. 설계

### 5.1 개념

- 일정 행의 `for_user_id`: `null` = 모두, 값 = 그 사람만.
- **내 동선에 들어가는 일정** = 그날 일정 중 `for_user_id IS NULL OR for_user_id = 나`. 이 거르기 뒤의 동선 계산(`buildDayRoute`, 밤 숙소 #91, 같은 장소 합치기)은 지금과 같다.
- 합류·해산은 따로 표시하지 않는다. 내 일정과 모두 일정을 순서대로 이으면 "부산역(나) → 서울역(모두) → …"이 된다.
- 이 규칙은 날짜를 가리지 않는다. 가운데 날에 "나만" 일정을 넣어도 같은 규칙으로 동작한다(목표는 아니지만 막지도 않는다).
- 여행에 사람이 혼자(주인만)면 새 일정 양식에 "누구" 칸을 보이지 않는다. 다만 지인이 나간 뒤 주인의 "나만" 일정이나 §5.3 경쟁으로 남은 값이 있을 수 있으므로, **값이 있는 일정은 혼자 여행에서도 고치기 양식에 "누구" 칸을 보이고 이름표도 보인다**(칸을 숨긴 채 저장해 값이 몰래 모두로 바뀌지 않게). 값이 모두 null 인 혼자 여행은 화면이 지금과 같다. (빌더 확인 뒤 내 판단)

### 5.2 DB (마이그레이션 0009, 파괴적 아님)

```sql
ALTER TABLE "schedule_items" ADD COLUMN "for_user_id" text;
ALTER TABLE "schedule_items" ADD CONSTRAINT "schedule_items_for_user_id_user_id_fk"
  FOREIGN KEY ("for_user_id") REFERENCES "public"."user"("id") ON DELETE cascade ON UPDATE no action;
```

- `src/db/schema.ts` 에 `forUserId: text("for_user_id").references(() => user.id, { onDelete: "cascade" })` 를 더하고 `npm run db:generate`. 위 SQL 은 예상이고 PR 에는 생성된 파일 전문을 싣는다.
- nullable 칸 추가와 FK 추가뿐이다. 기존 행은 모두 `null`(= 모두)이 되어 화면이 그대로다. DROP·타입 변경·NOT NULL 없음 → 파괴적 아님.
- 사용자 계정이 지워지면(앱에는 그 기능이 없다) 그 사람의 "나만" 일정도 지워진다(계정 삭제 시 `trip_members` 가 cascade 되는 것과 같은 결).
- 색인은 더하지 않는다. 일정은 늘 `(trip_id, date)` 색인으로 여행 단위로 읽는다.

### 5.3 "누구" 값 쓰기 (보안)

- 입력: 일정 양식의 `forUserId` 필드 하나. 값은 `""`(모두) 또는 사용자 id 문자열. `src/lib/schedule-input.ts` 에서 길이·형식만 거른다(Better Auth 사용자 id 는 uuid 가 아니므로 `isUuid` 로 거르지 않는다. 길이 상한과 공백 없음 정도).
- **여행 사람인지는 쓰는 문 안에서 확인한다.** `for_user_id` 가 null 이 아니면, 넣기·고치기 문의 조건에 "그 값이 이 여행의 주인(`trips.user_id`)이거나 `trip_members` 에 그 여행·그 사용자 행이 있음"을 더한다. 조건이 안 맞으면 0행 → 액션은 "함께하는 사람을 다시 골라 주세요."(필드 오류). 일정 쓰기 함수 넷의 분기 여섯 모두(`createScheduleItem` 장소 있음/없음, `createScheduleItemWithNewPlace`, `updateScheduleItem` 장소 있음/없음, `updateScheduleItemWithNewPlace`)에 같은 조건을 넣는다.
  - `createScheduleItem` 의 장소 없는 분기는 지금 여행을 먼저 읽고 `values()` 로 넣는 두 단계라 조건을 붙일 문이 없다. `insert … select … from trips where …` 한 문으로 바꾼다.
  - 장소 있는 분기의 `insert … select` 는 모든 열을 테이블 정의 순서대로 고른다(같은 파일 주석). 새 열 `for_user_id` 를 schema 의 열 순서에 맞는 자리에 넣는다. 조건은 `schedule-items.ts` 의 함수 하나(`forUserAllowed(tripIdSql, forUserId)` 같은)로 모은다.
  - 0행이 "일정이 없음"인지 "사람이 아님"인지는 액션이 한 번 더 읽어 가린다(일정을 읽을 수 있으면 사람 문제). 지금 장소 조건 실패를 다루는 방식과 같은 결로 한다.
- 누가 바꿀 수 있나: 함께하는 사람은 지금처럼 모든 일정을 고칠 수 있다. "누구"도 아무나 바꾼다(남의 일정을 대신 넣는 것도 막지 않는다, 사용자 확인).
- 경쟁: 사람 확인과 그 사람의 나가기가 동시에 일어나면 나간 사람의 일정이 남을 수 있다. 남으면 화면에서는 "나간 사람" 이름표로 접힌 줄로 보이고 아무의 동선에도 들어가지 않는다. 고치기 양식은 "누구"를 모두로 바꿀 수 있게 한다. 받아들인다(#15 의 동시 참여 20명 초과와 같은 결).

### 5.4 나가기·내보내기 (`trip-members.ts` 의 `removeMemberAndPrivateRows`)

지금 CTE(`removed` → `gone_items`(그 사람 내 돈 행) → `gone_budgets`)에 더한다.

1. `gone_sched_src`: `schedule_items` 중 `trip_id, for_user_id` 가 `removed` 에 있는 행(id, date, 제목 규칙은 `deleteScheduleItem` 과 같음: 일정 제목 → 장소 이름표 → 적은 장소 글자 → "지운 일정", `EXTRA_TITLE_MAX` 로 자름).
2. `moved_sched_money`: 그 일정들에 붙은 `budget_items` 중 **나가는 사람의 내 돈 행이 아닌 것**(모임 행 + 다른 사람의 내 돈 행)을 일정 밖 항목으로 옮긴다(`schedule_item_id = NULL`, title, date). 나가는 사람의 내 돈 행은 `gone_items` 가 지운다(두 CTE 가 같은 행을 건드리지 않게 조건을 서로 배타로).
3. `gone_sched`: 그 일정들을 지운다.

- 일정을 지울 때(`deleteScheduleItem`)는 모임 행을 cascade 로 지우지만, 나가기에서는 **모임 행도 옮긴다.** 사람이 직접 지운 것이 아니라 시스템 동작이라, 모임 통장에서 실제로 나간 표 값이 경고 없이 사라지면 안 되기 때문이다(사용자 확인).
- 옮긴 모임 행이 cascade 로 지워지지 않는 까닭은 `deleteScheduleItem` 주석의 설명과 같다(RI 트리거는 문 끝에 새 스냅숏으로 돈다). 구현 뒤 실제 DB(임시 Neon 브랜치 또는 마이그레이션 적용 뒤 테스트 계정)에서 확인한다.
- 일정 밖 항목 300건 상한은 옮기기에서 검사하지 않는다(#89 의 일정 삭제와 같음, 남은 지적으로 적음).
- 주인은 나갈 수 없으므로 주인의 "나만" 일정은 이 경로로 지워지지 않는다.
- 나가기·내보내기 확인 문구(`member-buttons.tsx`)에 그 사람만의 일정도 지워진다는 것을 더한다. 예: "나가면 내 돈 지출·내 예산과 나만의 일정이 지워져요. 나만의 일정에 적은 모임 통장 금액은 일정 밖 항목으로 남아요." (내 판단)

### 5.5 동선 거르기 (`src/lib/day-route.ts`)

- 순수 함수 하나를 더한다: `routeItemsFor(items, viewerId)` → `for_user_id === null || for_user_id === viewerId` 인 행만(순서 유지). `ScheduleRow` 에 `forUserId: string | null` 을 더한다.
- `routesByDate` 를 부르는 세 곳(`map-section.tsx`, `schedule-section.tsx`, `day-route-loader.ts`)이 모두 **같은 함수로 거른 뒤** 넘긴다. 셋이 어긋나면 일정표 이동 줄과 지도·구간 결과가 서로 다른 동선을 가리키게 되므로(#37 서명), `routesByDate` 에 `viewerId` 를 인자로 넣어 안에서 거르게 하는 쪽을 권한다(빌더 판단).
- `day-route-loader.ts` 는 이미 `userId` 를 받으므로, Google 구간 요청도 내 동선 구간만 묻는다(남의 일정 구간은 서버 키로 묻지 않는다).
- `daySignature` 는 그대로다(거른 뒤의 동선으로 만들어지므로 사람마다 다르다. 저장소는 페이지·사람 단위라 충돌 없음).

### 5.6 화면

**일정 양식**(`schedule-item-form.tsx`): 여행 사람이 둘 이상일 때만 "누구" 칸.

```
누구   [모두] [나] [지인] [지인2]
```

- 한 줄 고르기(라디오 모양 버튼). 순서: 모두 → 나 → 나머지 사람(`listTripPeople` 순서, 주인 먼저). 새 일정의 처음 값은 모두.
- 이름은 `listTripPeople` 의 `name`. 보는 사람 본인은 "나".
- 고치기 양식은 지금 값을 처음 값으로. 지금 값이 이제 여행 사람이 아니면(§5.3 경쟁) "나간 사람"으로 보이고 다른 값으로 바꿀 수 있다.

**일정표**(`schedule-day-items.tsx`):

- 모두 일정: 지금과 같다.
- 내 일정: 지금 줄 + 작은 이름표 `[나]`.
- 남의 일정: **한 줄로 접힌 줄**. 시각 · 제목(또는 장소) · 이름표. 누르면 펼쳐져 보통 줄(완료 체크, 고치기, 금액 등)이 된다. 역 동그라미·레일에서 이 줄은 동선 밖이라는 것이 보이게(빈 레일 또는 흐린 표시, 빌더 판단).

```
08:00  ● 부산역 KTX                [나]  ₩59,800
       ┊ 08:30 동대구역 KTX · 지인   ▸
       ⋮ 2시간 40분
11:00  ● 서울역 합류
```

- 이동 시간 줄(#37)은 지금처럼 `toItemId` 일정 줄 위에 붙는다. 내 동선 구간만 있으므로 남의 일정 줄 위에는 붙지 않는다.
- 끌어서 순서 바꾸기(#41): 남의 접힌 줄도 그날 순서의 한 자리다. 순서 저장은 지금처럼 그날 **모든** 일정 id 를 보낸다(검증 `listDayOrder` 는 그대로). 접힌 줄을 끌 수 있게 할지는 빌더 판단(끌 수 없어도 내 줄을 그 주위로 옮길 수 있으면 된다).

**지도**(`map-section.tsx`·`trip-map-panel.tsx`): N일차 선·핀·번호·"아침엔 🏨 X에서 출발"이 내 동선만으로 그려진다. `map-section.tsx` 는 `routesByDate` 밖에서도 일정 행을 쓴다: N일차 탭의 좌표 없는 일정 안내(`unlocatedCount`)도 **같은 거르기 함수로 거른 행**으로 센다. [전체] 탭(가 볼 곳 목록과 장소별 "N일차 일정" `scheduleDays`)은 그대로 모든 일정을 쓴다.

**예산**: 바꾸지 않는다. 남의 "나만" 일정에 붙은 모임 통장 금액은 지금처럼 예산 카드 날짜별 표에 들어가 모두가 본다(#89 규칙). 남의 내 돈 금액은 지금처럼 그 사람만 본다.
- "나만" 일정에 금액을 처음 적을 때 [모임]/[내 돈] 처음 고른 쪽은 **지금처럼 여행 방식이 정한 값**으로 둔다. 각자 표 값을 모임 통장에서 내는 경우(#89 사용자의 경우)가 있기 때문이다. (내 판단)

### 5.7 데이터 흐름

- `ScheduleSection` 은 이미 `userId` 를 받는다. 일정 줄 데이터(`RowItem`)에 `forUserId`·`forLabel`("나"/이름/"나간 사람"/null)을 더한다. 사람 목록은 `listTripPeople(userId, trip.id)` 로 한 번 읽어 양식 선택지와 이름표에 쓴다(`MembersSection` 도 읽으므로 `cache` 로 감싸 한 요청에 한 번).
