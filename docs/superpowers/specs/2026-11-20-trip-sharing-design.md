# 지인과 여행 함께 보기·고치기 (#15)

2026-11-20. 사용자 승인 대기.

## 1. 왜

여행을 지인과 함께 계획한다. 초대받은 사람도 **같이 편집**한다(사용자). 보기만 하는 공유가 아니다.

지금은 여행 하나에 주인(`trips.user_id`) 한 사람뿐이다. 남의 여행은 "찾을 수 없음"이다. 이번 일은 이 규칙을 "주인이거나 함께하는 사람"으로 넓히는 것이다. #53(전체 디자인 정리)이 이 일 다음 순서다. 그래서 화면은 기존 스타일을 따라 필요한 만큼만 바꾼다.

## 2. 목표 · 비목표 · 반목표

- 목표
  - 주인이 여행 화면에서 **초대 링크**를 만들어 카톡 등으로 보낸다. 받은 사람이 링크를 열어 Google 로 로그인하고 [참여] 를 누르면 **함께하는 사람**이 된다(사용자: 방법 1).
  - 함께하는 사람은 주인과 똑같이 여행 정보(제목·목적지·날짜·메모), 일정, 가 볼 곳, 기준점, 예산을 보고 고친다(사용자: "같이 편집").
  - **주인만** 하는 것: 여행 삭제, 초대 링크 만들기·새로 만들기·끄기, 함께하는 사람 내보내기. 함께하는 사람은 스스로 **나가기**를 할 수 있다(제안, 사용자 이의 없음).
  - "내 여행" 목록에 공유받은 여행도 함께 나온다. 카드에 "○○님의 여행" 표시를 붙인다.
  - 여행 화면에서 함께하는 사람(주인 포함) 목록이 보인다.
- 비목표
  - 예산을 사람별로 나누기: 누가 냈는지, 나눠 내기, 정산. 예산은 **지갑 하나**다(사용자: 1). 모두가 같은 예산에 지출을 적는다.
  - 실시간 반영. 상대가 고친 내용은 새로 고치거나 다른 화면에 다녀오면 보인다(제안, 사용자 이의 없음).
  - 보기 전용 권한, 권한 단계 나누기. 함께하는 사람은 모두 편집자다.
  - 이메일 초대, 메일·알림 보내기.
  - 주인 넘기기. 주인이 탈퇴(계정 삭제)하면 여행이 지워진다(지금과 같음, `on delete cascade`).
  - 누가 무엇을 고쳤는지 기록(변경 이력).
  - 링크 만료 기한. 주인이 끄거나 새로 만들 때까지 유효하다(제안).
- 반목표 (돌아가도 실패인 것)
  - 초대받지 않은 사람이 여행이나 그 하위 데이터(일정·장소·기준점·예산)를 읽거나 바꾼다. 특히 하위 id 를 섞어 보내서 남의 여행 데이터에 닿는다.
  - 함께하는 사람이 여행을 지우거나, 링크를 바꾸거나, 다른 사람을 내보낸다.
  - 내보낸 사람·나간 사람이 열어 둔 화면이나 옛 링크로 계속 고친다. 주인이 링크를 끄거나 새로 만든 뒤에도 옛 링크로 들어온다.
  - 링크를 미리 불러오기(카톡 미리보기, Next 링크 prefetch)만 해도 참여된다.
  - 초대 화면이나 함께하는 사람 목록이 이메일 주소를 드러낸다.
  - DB 를 읽기만 할 수 있는 사람(읽기 전용 Neon MCP, 백업)이 `trips` 에 저장된 값으로 초대 링크를 만들어 여행에 들어온다. 잠깐 남는 곳은 받아들인다(빌더 판단, §5.3 의 6).
  - 카톡으로 받은 링크를 열었는데 로그인에서 막혀 참여할 방법이 없다(§5.7).
  - 공유 기능 때문에 일정표·지도 화면이 느려진다(목록·접근 조건이 무거워진다).

## 3. 제약

- 마이그레이션 PR(CLAUDE.md '마이그레이션 PR'): 새 테이블 하나, `trips` 에 nullable 칸 둘. 파괴적이지 않다. 자동 머지 없이 사람이 SQL 을 보고 `human-approved` 를 붙이면 `npm run db:migrate` 를 실행한다(실행 직전 사람 확인).
- 위험 경로: `src/db/schema.ts`, `drizzle/**`. 인증·소유권 코드를 바꾸므로 `/security-review` 를 받는다. `src/lib/auth.ts`·`session.ts` 는 바꾸지 않는다.
- 여행 접근 조건은 `accessibleTrips(userId)`(`src/db/queries/trips.ts`) 하나다. 일정·장소·기준점·예산 쿼리가 모두 이 조건을 같은 SQL 문 안에 넣는다. 이 조건만 바꾸면 하위 데이터는 그대로 따라온다.
- neon-http 에는 트랜잭션이 없다. 조건부 쓰기는 한 SQL 문(`insert … select … where`, 데이터를 바꾸는 CTE)으로 한다.
- 로그인은 Google 뿐이다. 로그인 버튼의 `callbackURL` 이 지금은 `"/"` 로 고정이다(`auth-buttons.tsx`).
- 사용자에게 보이는 문구는 한국어.

## 4. 방법 (사용자가 1 을 고름)

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| **1** | **초대 링크**: 여행마다 비밀 링크 하나. 열고 로그인하고 [참여] | 상대 이메일을 몰라도 된다. 단톡방에 한 번 올리면 여러 명이 들어온다 | 링크가 새면 모르는 사람이 들어올 수 있다. 목록·내보내기·링크 새로 만들기로 막는다 |
| 2 | 이메일로 초대: 주인이 Gmail 주소를 적어 두면 그 계정에 나타남 | 링크가 새도 문제없다 | Google 로그인 주소를 정확히 알아야 한다. 틀리면 왜 안 되는지 알기 어렵다. 초대 목록 관리가 따로 필요하다 |
| — | 로그인 없는 공개 보기 링크 | — | "같이 편집"에 맞지 않아 뺐다 |

## 5. 설계

### 5.1 데이터 (마이그레이션 0007)

```
trip_members
  trip_id    uuid  not null  references trips(id) on delete cascade
  user_id    text  not null  references user(id)  on delete cascade
  joined_at  timestamptz not null default now()
  primary key (trip_id, user_id)
  index trip_members_user_id_idx (user_id)

trips 에 더함
  invite_token_hash        text  null  unique
  invite_token_created_at  timestamptz null
```

- 주인은 지금처럼 `trips.user_id` 다. `trip_members` 에는 주인이 아닌 사람만 넣는다. 주인을 멤버 행으로 옮기지 않으므로 기존 데이터를 바꿀 일이 없다.
- 초대 링크의 비밀값은 **해시만** 저장한다(SHA-256, hex). 그래서 DB 를 읽을 수만 있는 사람은 링크를 만들 수 없다(§2 반목표). 대신 주인도 나중에 링크를 다시 볼 수 없다. 링크를 다시 보내려면 [새 링크 만들기] 를 누른다. 그러면 옛 링크는 죽고, 이미 참여한 사람에게는 영향이 없다.
- 비밀값은 32바이트 난수(`crypto.randomBytes`)를 base64url 로 적는다(43글자). 추측할 수 없으므로 시도 횟수 제한은 두지 않는다.
- 함께하는 사람은 주인을 빼고 **여행당 20명**까지다(빌더 판단). 참여 쿼리 안에서 센다. 동시에 참여하면 조금 넘을 수 있다. 장소 100개 상한(#13)과 같은 수준이다.

### 5.2 접근 조건

`src/db/queries/trips.ts`:

```ts
// 보기·고치기: 주인이거나 함께하는 사람
export function accessibleTrips(userId: string): SQL {
  return or(
    eq(trips.userId, userId),
    exists(
      db.select({ one: sql`1` }).from(tripMembers)
        .where(and(eq(tripMembers.tripId, trips.id), eq(tripMembers.userId, userId))),
    ),
  );
}

// 주인만: 여행 삭제, 초대 링크, 내보내기
export function ownedTrips(userId: string): SQL {
  return eq(trips.userId, userId);
}
```

- 일정·장소·기준점·예산 쿼리는 그대로다. 이미 `accessibleTrips` 를 같은 SQL 문 안에 넣고 있다. 구현할 때 이 네 파일과 `day-route` Route Handler 가 모두 이 조건을 거치는지 다시 확인한다.
- `deleteTrip` 만 `ownedTrips` 로 바꾼다. 함께하는 사람이 삭제를 보내면 바뀐 행이 없으니 "찾을 수 없음"이 된다.
- `updateTrip` 은 `accessibleTrips` 그대로 둔다. 함께하는 사람도 제목·날짜를 고친다.
- `getTrip` 은 화면이 버튼을 고를 수 있도록 `isOwner: boolean` 을 함께 돌려준다(`trips.user_id = userId`). 서버의 권한 판단은 화면 값이 아니라 각 쿼리의 조건으로 한다.

### 5.3 초대 링크 흐름

주소: `/invite/<비밀값>`.

1. **주인이 링크 만들기**: 여행 화면 "함께하는 사람" 칸의 [초대 링크 만들기]. Server Action 이 비밀값을 만들어 해시와 시각을 `trips` 에 쓴다(`where id = ? and ownedTrips`). 원문은 응답으로 한 번만 돌려준다. 화면에 링크 글자와 [복사] 를 보인다. 링크가 이미 켜져 있으면 버튼 이름은 [새 링크 만들기] 다. 누르기 전에 "지금 링크는 더 이상 쓸 수 없어요. 이미 참여한 사람은 그대로예요." 로 확인한다.
2. **링크 끄기**: 해시와 시각을 `null` 로 쓴다(주인만).
3. **받은 사람이 링크 열기** (`/invite/[token]` 페이지, Server Component):
   - 로그인하지 않았으면 "초대받은 여행에 참여하려면 로그인하세요" 와 Google 로그인 버튼을 보인다. 로그인 뒤에는 같은 초대 주소로 돌아온다. `GoogleSignInButton` 에 `callbackURL` prop 을 더한다. 기본값은 `"/"` 이고, 값은 이 페이지가 서버에서 만든 상대 경로뿐이다.
   - 로그인했으면 해시로 여행을 찾는다. 이때 여행 제목, 주인 이름, 기간만 읽는다(`src/db/queries/trip-members.ts`).
     - 링크가 맞지 않음(꺼짐·새로 만듦·형식 틀림): "초대 링크가 만료됐거나 잘못됐어요. 여행을 만든 분께 새 링크를 받아 주세요." `notFound()` 가 아니라 이 안내를 보인다. 형식이 틀린 값(43글자 base64url 이 아님)은 쿼리 전에 거른다.
     - 이미 주인이거나 함께하는 사람: 여행 화면으로 `redirect`.
     - 그 밖: "○○님의 '△△' 여행 (기간) 에 함께할까요?" + [참여] 버튼.
   - 페이지를 그리기만 해서는 아무것도 쓰지 않는다. 미리 불러오기로는 참여되지 않는다(§2 반목표).
4. **[참여]** Server Action(`joinTripAction(token)`): `getCurrentUser()` → 비밀값 형식 검사 → 한 SQL 문으로 다시 확인하고 넣는다.
   ```sql
   insert into trip_members (trip_id, user_id)
   select t.id, $me from trips t
   where t.invite_token_hash = $hash
     and t.user_id <> $me
     and (select count(*) from trip_members m where m.trip_id = t.id) < 20
   on conflict do nothing
   returning trip_id
   ```
   - 넣었으면 여행 화면으로 간다.
   - 넣지 못했으면 다시 따져서 안내한다. 이미 멤버면 여행 화면으로 간다. 링크가 틀렸으면 만료 안내를 보이고, 20명이 찼으면 "함께하는 사람이 너무 많아요(20명까지)" 를 보인다.
5. **Referer 로 새지 않게**: 초대 페이지는 `referrer: "no-referrer"`(Next metadata)로 둔다. 외부 스크립트(Google 지도 등)를 불러오지 않는다.
6. **원문이 잠깐 남는 곳 (빌더 판단, 받아들임)**: 비밀값이 주소에 있으므로 Vercel 요청 로그에 남는다. 또 로그인 중에는 Better Auth 가 `callbackURL`(초대 주소)을 `verification` 표에 최대 10분 둔다(`account.storeStateStrategy` 기본값 `"database"`). 이 둘을 막으려면 `src/lib/auth.ts` 를 고치거나 링크를 조각(`#`)·쿠키 방식으로 바꿔야 한다. 둘 다 짧게만 남고, 새면 [새 링크 만들기] 로 막을 수 있어 그대로 둔다. PR "남은 지적"에 적는다.

### 5.4 함께하는 사람 칸 (여행 화면)

여행 머리(제목·고치기·삭제 아래)에 작은 칸 하나를 둔다. 기존 카드 스타일을 따른다.

```
함께하는 사람
 (사진) 박○○ · 주인
 (사진) 김○○                [내보내기]   ← 주인에게만 버튼
 (사진) 이○○ (나)            [나가기]    ← 함께하는 사람 본인에게
[초대 링크 만들기]                        ← 주인에게만
```

- 보이는 것은 이름과 사진뿐이다. 이메일은 쿼리에서 고르지 않는다.
- 여행 화면 머리의 [삭제] 는 주인에게만 보인다. [고치기] 는 모두에게 보인다.
- **내보내기**(주인): `delete from trip_members where trip_id = ? and user_id = ? and trip_id in (주인 소유 여행)`. 누르기 전에 확인한다. 내보낸 사람이 링크가 아직 켜져 있으면 다시 들어올 수 있다는 것도 안내한다: "링크가 켜져 있으면 다시 들어올 수 있어요. 막으려면 새 링크를 만드세요."
- **나가기**(본인): `delete from trip_members where trip_id = ? and user_id = $me`. 확인한 뒤 `/trips` 로 간다.
- 링크 원문은 만든 직후 그 화면에서만 보인다. 새로 고치면 "초대 링크가 켜져 있어요 (11월 20일 만듦) [새 링크 만들기] [끄기]" 로 바뀐다.

### 5.5 여행 목록

- `listTrips(userId)` 가 `accessibleTrips` 로 공유받은 여행도 함께 가져온다. 이때 주인 이름도 함께 가져온다(`user` 조인, `name` 만).
- 다가오는·지난 여행 나누기는 그대로다. 공유받은 여행 카드에는 "○○님의 여행" 한 줄을 더한다.
- 제목 "내 여행" 과 "← 내 여행" 링크는 그대로 둔다. 문구 정리는 #53 에서 한다.

### 5.6 무효화와 열어 둔 화면

- 링크·멤버 동작 뒤에는 `revalidatePath(`/trips/${id}`)` 와 `/trips` 를 무효화한다(기존 동작과 같다).
- 내보낸 사람이 열어 둔 화면에서 저장하면 쿼리 조건에 걸려 기존 "찾을 수 없음"이나 저장 실패가 된다. 따로 처리하지 않는다.
- 동시에 고치는 경우의 규칙(일정 순서 다시 쓰기, 예산 통화 바꾸기 등)은 지금 한 사용자가 두 창을 열었을 때와 같다. 새 위험은 없지만 일어날 확률은 높아진다. 기존 남은 지적(#41 순서, #14 설정·금액 동시 쓰기)이 사람 둘에게도 그대로 해당한다.

### 5.7 앱 안 브라우저 (사용자: 1)

카톡에서 링크를 누르면 카톡 안 브라우저가 열린다. Google 은 앱 안 브라우저에서 로그인을 거부한다(`disallowed_useragent`). 초대 링크는 주로 카톡으로 보내므로, 그대로 두면 받은 사람 대부분이 로그인에서 막힌다. 이 앱의 첫 화면(`/`)도 같다.

- 로그인 버튼이 보이는 두 화면(첫 화면, 로그인하지 않은 초대 화면)에서 클라이언트 조각 하나가 `navigator.userAgent` 를 본다.
  - **카톡**(`KAKAOTALK`): 화면에 들어오면 바로 `kakaotalk://web/openExternal?url=<지금 주소, encodeURIComponent>` 로 보내 기본 브라우저(크롬·사파리)에서 같은 주소를 다시 연다. 카톡 화면에는 "브라우저에서 열었어요. 열리지 않으면 아래 버튼을 눌러 주세요." 와 [브라우저로 열기](같은 주소), [링크 복사] 를 남긴다.
  - **그 밖 앱 안 브라우저**(인스타그램 `Instagram`, 페이스북 `FBAN`·`FBAV`, 라인 `Line/`, 네이버 `NAVER(inapp`, 안드로이드 웹뷰 `; wv)`): 자동으로 넘기지 않는다. "Google 로그인은 이 앱 안에서는 안 돼요. 크롬이나 사파리에서 열어 주세요." 와 [링크 복사] 를 보인다. Google 로그인 버튼은 그대로 둔다(잘못 알아봤을 때 막히지 않게).
  - 그 밖: 지금처럼 로그인 버튼만 보인다.
- 넘기는 주소는 지금 페이지 주소(`location.href`) 뿐이다. 외부 입력으로 주소를 만들지 않는다.
- 사용자 에이전트 판별은 순수 함수(`src/lib/in-app-browser.ts`, `node --test`)로 둔다. 판별 문자열은 바뀔 수 있다. 실제 카톡 동작은 프로덕션에서 사용자가 확인한다.

## 6. 시험·확인

- 단위 시험: 비밀값 형식 검사와 해시(순수 모듈 `src/lib/invite-token.ts`, `node --test`, 해시에는 `node:crypto` 만 쓴다), 앱 안 브라우저 판별(`src/lib/in-app-browser.ts`).
- 브라우저 확인(로컬 dev, 테스트 계정 둘: A=주인, B=초대받는 사람, C=남. 넣기·지우기 전 SQL 을 보이고 사용자 확인):
  1. A 가 링크를 만든다 → B 가 로그인 안 한 채 링크를 연다 → 로그인 화면이 보인다. 클라우드에는 Google 키가 없어 실제 로그인 왕복은 못 한다. 이 왕복은 세션 쿠키를 붙인 채 다시 여는 것으로 대신한다.
  2. B 가 [참여] → 목록에 "A님의 여행" → 일정·장소·예산을 고칠 수 있다. [삭제] 와 [초대 링크] 는 없다.
  3. B 로 삭제·링크 만들기·내보내기 Server Action 을 직접 보내도(`page.route` 로 바꿔 보내기) 실패하고, DB 는 그대로다.
  4. C 는 여행 주소와 하위 id 섞어 보내기 모두 "찾을 수 없음"이다(기존 소유권 확인 반복).
  5. A 가 새 링크를 만들면 옛 링크는 만료 안내가 뜬다. A 가 B 를 내보내면 B 의 목록에서 사라지고, B 의 열린 화면에서 저장하면 실패한다.
  6. B 가 나가기 → 목록에서 사라진다.
  7. 사용자 에이전트를 카톡·인스타그램으로 흉내 내 첫 화면과 초대 화면을 연다. 카톡은 `kakaotalk://` 주소로 가려는 이동을, 인스타그램은 안내와 [링크 복사] 를 확인한다.
- 프로덕션 확인(사용자): 실제 지인 Google 계정으로 카톡 링크 → 바깥 브라우저 → 로그인 → 참여 → 같이 고치기.
