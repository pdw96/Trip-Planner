# 여행별 예산과 지출 (#14)

2026-11-20. 사용자 승인 대기.

## 1. 왜

여행 예산을 **짤 때** 쓴다(사용자). 그 뒤 실제 지출이 쌓이면 예산 대비 얼마나 초과했는지, 얼마나 여유가 있는지 보고, **남은 일정**을 정한다. 초과면 이후 일정을 줄이고, 여유면 이후 일정에 여유를 더 둔다.

그래서 총액 하나로는 모자란다. "3일째까지 60만 원 썼다"가 초과인지는 그때까지 얼마를 쓸 계획이었는지 알아야 판단할 수 있다. 예산을 일정에 붙여서, 실제와 예상을 항목마다 비교하고 남은 일정의 예상 비용을 본다.

비용을 어디까지 넣을지는 사람마다 다르다(사용자). 현지 경비만 관리하는 사람도, 항공·숙소까지 총 예산에 넣는 사람도 있다. 해외여행에서는 환전해서 현지 통화로 쓰므로 현지 통화로 적는 게 자연스럽다. 미리 예약하는 것은 보통 원화로 내지만, 아닐 수도 있으니 결제한 날의 환율로 계산되면 좋겠다(사용자).

## 2. 목표 · 비목표 · 반목표

- 목표
  - 여행마다 **총 예산** 하나를 정한다. 판단의 기준선이다.
  - 일정마다 **예상 비용**과 **실제 지출**을 적는다. 일정에 딸리지 않는 돈(항공권, 계획에 없던 간식·택시)은 "일정 밖 항목"으로 적는다.
  - 판단: **이대로 가면**(실제를 적은 항목은 실제, 아직 안 적은 항목은 예상) 합계를 총 예산과 비교해 초과·여유를 보인다. 실제를 적은 항목이 예상보다 얼마나 더·덜 들었는지, 남은(실제를 안 적은) 항목의 예상이 얼마인지도 보인다.
  - 날짜별 예상·실제 합계를 보인다(날짜별 예산을 따로 입력하지는 않는다).
  - 통화: 여행마다 **예산 통화** 하나와, 필요하면 **현지 통화** 하나 + **예정 환율**. 현지 통화로 적은 **예상**은 예정 환율로, **실제**는 **결제일 환율**로 예산 통화로 바꾼다. 결제일 환율은 자동으로 받아 채우고(유럽중앙은행 기준환율), 사용자가 고칠 수 있다(사용자 결정 (나)).
- 비목표
  - 분류(식비·교통·숙소…)와 분류별 예산. 판단 단위가 일정이다. 필요하면 나중에 붙인다.
  - 누가 냈는지·나눠 내기·정산. #15 공유 뒤에 따로 본다.
  - 세 번째 통화. 한 여행에 통화는 많아야 둘(예산·현지)이다.
  - 영수증 사진, 카드 내역 가져오기.
  - 날짜별 예산 직접 입력. 날짜별 합계는 일정 예상에서 계산한다.
  - 예산 설정 지우기. 한 번 정하면 금액·환율은 고칠 수 있지만, 설정 행 자체를 지우는 버튼은 두지 않는다.
- 반목표 (돌아가도 실패인 것)
  - 지난 실제 지출의 원화(예산 통화) 값이 나중에 저절로 바뀐다(환율을 다시 받아서 등). 결제일 환율은 저장한 순간 고정된다.
  - 금액이 부동소수점 오차로 1원씩 어긋난다.
  - 남의 여행 일정 id 를 섞어 보내 그 일정에 금액이 붙는다.
  - 환율 API 가 느리거나 죽어서 지출을 저장할 수 없다.
  - 통화를 바꿔서, 이미 적은 금액이 어느 통화인지 알 수 없게 되거나 엉뚱한 환율로 합쳐진다.
  - 예산 기능 때문에 일정표·지도 화면이 느려지거나 일정 코드가 복잡해진다.

## 3. 제약

- 마이그레이션 PR(CLAUDE.md '마이그레이션 PR'): 새 테이블 둘(§5.1), 파괴적 아님. 자동 머지 없이 사람이 SQL 을 보고 `human-approved` → `npm run db:migrate`(실행 직전 사람 확인) → 자동 머지. 위험 경로는 `src/db/schema.ts`, `drizzle/**` 뿐(새 의존성 없음).
- 금액은 정수(통화의 최소 단위)로 저장한다(이슈 #14). 환율은 `numeric` 으로 저장한다.
- 여행 접근 조건은 `accessibleTrips(userId)` 하나(#15 공유가 그것만 바꾸도록). 하위 쿼리는 하위 id 와 여행 id 를 같은 SQL 문 안에서 함께 묶는다(`schedule-items.ts`·`places.ts` 와 같은 방식).
- neon-http 에 트랜잭션이 없다. 조건부 쓰기·여러 행 쓰기는 한 SQL 문(조건부 `update … where not exists`, 데이터를 바꾸는 CTE)으로 한다.
- 단위 시험 대상 순수 모듈(`src/lib/*.ts`)은 다른 모듈을 import 하지 않는다.
- `next.config.ts` 에 `cacheComponents: true`. 외부 호출 캐시는 `holidays-api.ts` 처럼 `"use cache"` + `cacheLife` 로 한다(Next 16 문서 확인).
- 클라우드 세션은 `api.frankfurter.dev` 접속이 막혀 있다(2026-11-20 확인, 프록시 403). §6 참고.
- 사용자에게 보이는 문구는 한국어.

## 4. 방법

### 4.1 예산을 무엇에 붙일까 (사용자가 A 를 고름, B 를 포함해서)

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| **A** | **일정마다 예상·실제 + 일정 밖 항목, 총 예산 기준으로 판단** | 남은 일정 중 무엇을 줄이고 늘릴지 바로 보인다. 기존 일정표 위에 붙는다 | 계획에 없던 지출은 "일정 밖 항목"으로 따로 적는다 |
| B | 날짜별 예산 + 날짜만 붙은 지출 | 입력이 가볍다 | 초과는 알아도 무엇을 바꿀지는 직접 따져야 한다 |
| C | 분류별 예산 | "식비가 넘친다"를 안다 | 날짜 흐름이 없어 여행 중간 판단이 어렵다 |

사용자: "A 로 가도 B 도 포함이지? 총 예산 기준이 맞지?" → 날짜별 합계(B)는 A 의 일정 예상에서 계산해 보이고, 판단은 총 예산 기준으로 한다.

### 4.2 어떤 돈을 넣을까 (둘 다 되게)

사용자가 처음엔 "현지 통화로 입력하면 되지 않나", 이어서 "총 예산에 교통·숙소까지 넣는 사람도 있다"고 했다. 한 구조로 둘 다 되게 한다.

| 쓰는 방식 | 설정 | 입력 |
|---|---|---|
| 국내 여행 | 예산 통화 원화 | 모두 원화 |
| 현지 경비만 | 예산 통화 엔화 | 모두 엔화, 환율 없음 |
| 항공·숙소까지 | 예산 통화 원화 + 현지 통화 엔화 + 예정 환율 | 금액마다 ₩ 또는 ¥, 합계는 원화 |

### 4.3 실제 지출의 환율 (사용자가 (나)를 고름)

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| (가) | 지출마다 환율 칸, 기본값은 예정 환율 | 외부 서비스 없음 | 결제일 환율을 직접 찾아 넣어야 해서 실제로는 안 고친다 |
| **(나)** | **결제일 기준환율을 자동으로 받아 채우고 행에 저장, 사용자가 고칠 수 있음** | 사용자가 원한 "결제 당시 일자의 환율"이 손 안 대고 들어간다 | 외부 API 하나. 대만 달러·베트남 동은 없음. 실제 환전·카드 환율과 1–2% 차이 |
| (다) | 실시간 환율로 늘 다시 계산 | — | 지난 지출 값이 날마다 바뀐다(반목표) |

환율 출처는 Frankfurter(`api.frankfurter.dev/v1`, 유럽중앙은행 기준환율, 키 없음, 무료)다. *(Claude 의 판단)* 한국수출입은행 환율 API 는 키가 필요하고, 다루는 통화가 비슷하며 영업일 당일 값만 준다.

## 5. 설계

### 5.1 데이터 (마이그레이션 0006)

**`trip_budgets`** — 여행당 한 행(설정).

| 칸 | 타입 | 뜻 |
|---|---|---|
| `trip_id` | uuid PK, FK trips on delete cascade | |
| `currency` | text not null | 예산 통화(ISO 4217, `^[A-Z]{3}$`) |
| `total_amount` | bigint not null, ≥ 0 | 총 예산(예산 통화 최소 단위) |
| `local_currency` | text null, ≠ `currency` | 현지 통화 |
| `planned_rate` | numeric(20,10) null, > 0 | 현지 통화 1 = 예산 통화 몇. `local_currency` 와 함께 있거나 함께 없다(check) |
| `created_at`·`updated_at` | | |

**`budget_items`** — 일정에 붙은 금액, 또는 일정 밖 항목.

| 칸 | 타입 | 뜻 |
|---|---|---|
| `id` | uuid PK | |
| `trip_id` | uuid not null, FK trips cascade | |
| `schedule_item_id` | uuid null, FK schedule_items **on delete cascade**, unique | 일정에 붙은 행. 일정 하나에 한 행 |
| `title` | text null | 일정 밖 항목 이름 |
| `date` | date null | 일정 밖 항목의 날짜. 비면 "여행 전체"(항공권 등) |

| `actual_amount`·`actual_currency` | bigint ≥ 0 · text, 함께 | 실제 |
| `actual_paid_on` | date null | 결제일. 실제가 현지 통화일 때만 값 |
| `actual_rate` | numeric(20,10) null, > 0 | 결제일 환율(현지 1 = 예산 통화 몇). 실제가 현지 통화일 때만 값 |
| `actual_rate_source` | text null, in (`ecb`, `manual`, `planned`) | 환율 출처. `actual_rate` 와 함께 |

check:
- 일정에 붙은 행은 `title`·`date` 가 null(이름·날짜는 일정을 따른다). 일정 밖 행은 `title` 이 not null.
- 예상이나 실제 중 하나는 있다. 둘 다 지우면 행을 지운다(앱이 한 문으로).
- index `(trip_id)`.

*(Claude 의 판단)*
- **일정을 지우면 그 일정의 예상·실제도 함께 지운다**(cascade). 일정 없는 금액을 "이름 없는 항목"으로 남기는 것보다 단순하다. 실제를 적은 일정을 지우면 그 지출도 합계에서 빠진다는 것을 일정 삭제 확인 문구에 덧붙이지는 않는다(일정 코드를 건드리지 않기 위해).
- 일정 밖 항목은 일정 테이블과 분리된 행이라 일정표·지도·동선에 나타나지 않는다.
- 여행 기간을 줄이면 날짜가 밖으로 나간 행은 "여행 기간 밖"에 모아 보인다(일정과 같은 방식). 합계에는 그대로 들어간다.
- 금액 상한: 최소 단위로 10^12 미만(원화 1조). 여행당 `budget_items` 300행 상한(넣기 전에 센다, 장소 100개 상한과 같은 방식).

### 5.2 통화 바꾸기 규칙

금액 행은 통화 코드를 들고 있으므로, 설정을 바꿀 때 저장된 금액의 통화가 설정에서 사라지면 안 된다(반목표).

- 총 예산·예정 환율: 언제든 고친다. 예정 환율을 고치면 현지 통화 **예상** 합계가 다시 계산된다(실제는 행마다 저장된 결제일 환율이라 그대로).
- 현지 통화 **추가**(없음 → 엔화): 언제든.
- 현지 통화 **바꾸기·없애기**: 그 통화로 적은 금액이 하나도 없을 때만.
- 예산 통화 바꾸기: 금액 행이 하나도 없을 때만. (현지 통화 실제 행의 저장된 환율이 옛 예산 통화 기준이라서다.)
- 위 조건은 쓰기 문 안에서 확인한다(`update … where not exists (select … from budget_items …)`). 거절하면 "이미 적은 금액이 있어 통화를 바꿀 수 없어요."

### 5.3 계산 (`src/lib/budget.ts`, 순수 모듈)

- **통화 목록**: 고를 수 있는 통화를 코드에 적어 둔다. 코드·기호·소수 자릿수·유럽중앙은행 지원 여부를 함께 둔다. *(Claude 의 판단)* 최소: KRW(0), JPY(0), USD(2), EUR(2), CNY(2), HKD(2), TWD(2, ECB 없음), THB(2), VND(0, ECB 없음), SGD(2), PHP(2), MYR(2), IDR(0, 실제로는 소수 안 씀), GBP(2), AUD(2), CAD(2), CHF(2). `Intl` 의 자릿수에 기대지 않는다. 런타임 데이터가 바뀌면 저장된 최소 단위의 뜻이 바뀌기 때문이다.
- **입력 해석**(`src/lib/budget-input.ts`): "12,000", "12000.5" 같은 글자 → 최소 단위 정수. 쉼표 허용, 그 통화 자릿수보다 긴 소수·음수·빈칸·상한 초과는 거절. 계산은 글자 단위로 하고 부동소수점을 쓰지 않는다.
- **바꾸기**: `toBudgetMinor(amountMinor, fromCurrency, budget)` — 예산 통화면 그대로. 현지 통화면 환율(예상은 `planned_rate`, 실제는 `actual_rate`)을 곱하고, 자릿수 차이를 맞춘 뒤 **행마다** 가장 가까운 최소 단위로 반올림(0.5 는 0 에서 먼 쪽). 환율은 문자열(numeric)로 받아 정수 비율로 바꿔 계산한다(BigInt).
- **요약**(`summarizeBudget(items, budget)`): 모두 예산 통화 최소 단위.
  - 총 예산 `B`
  - 예상 합계 `E` = Σ 예상
  - 실제 합계 `A` = Σ 실제
  - 실제를 적은 항목의 차이 `D` = Σ(실제 − 예상) — 실제가 있는 항목 모두. 예상 없이 실제만 있는 항목(계획에 없던 지출)은 예상 0 으로 셈한다. 그중 계획에 없던 지출 합계 `U` 도 따로 돌려준다. *(Claude 의 판단, 빌더 확인 반영: 그래야 계획 대비 넘은 돈이 모두 보인다)*
  - 남은 예상 `R` = Σ 예상 — 실제가 아직 없는 항목만
  - 이대로 가면 `P` = A + R
  - 여유 `B − P`(음수면 초과)
- **날짜별**: 항목의 날짜 = 일정에 붙은 행은 일정 날짜, 일정 밖 행은 `date`. 날짜 없음 → "여행 전체", 여행 기간 밖 → "여행 기간 밖". 날짜마다 예상·실제 합계.
- "지금까지"를 오늘 날짜로 자르지 않는다. 지난 날인데 실제를 안 적은 항목은 예상으로 셈한다(아마 썼는데 안 적었다고 보는 쪽이 안전하다). *(Claude 의 판단)*

### 5.4 결제일 환율 받기 (`src/lib/fx-api.ts`, server-only)

- `getEcbRate(date, from, to): Promise<{ rate: string; rateDate: string } | null>` — `GET https://api.frankfurter.dev/v1/{date}?base={from}&symbols={to}`. 주말·휴일이면 Frankfurter 가 그 전 영업일 값을 준다(`rateDate` 로 보인다).
- 지난 날짜의 값은 바뀌지 않으므로 `"use cache"` + 긴 `cacheLife`. 실패는 캐시하지 않는다(`holidays-api.ts` 처럼 안쪽 함수는 throw, 바깥 함수가 잡아 `null`). 시간 제한 5초. 실패하면 `[fx]` 로그 한 줄.
- 절대 저장을 막지 않는다(반목표): `null` 이면 예정 환율로 저장하고 출처 `planned`.
- 받지 않고 바로 `planned`: 결제일이 오늘(서울)보다 뒤, 또는 두 통화 중 하나가 ECB 미지원.
- 언제 받나: 실제 지출을 저장하는 Server Action 안에서, 실제가 현지 통화이고 다음 중 하나일 때.
  - 새로 적는 실제 지출
  - 결제일이나 통화가 바뀌었고, 사용자가 환율 칸을 직접 고치지 않았을 때
  - 출처가 `planned` 인 행을 사용자가 다시 저장할 때(결제일이 오늘 이전이면). 예정 환율은 원래 원한 값이 아니라 대신 들어간 값이라서, 사용자가 저장할 때마다 다시 시도한다. 저절로(백그라운드) 다시 받지는 않는다. *(Claude 의 판단, 빌더 확인 반영)*
  사용자가 환율을 직접 넣으면 그 값, 출처 `manual`. 출처가 `ecb`·`manual` 인 행은 금액만 고치면 저장된 환율을 그대로 둔다.

### 5.5 쿼리 (`src/db/queries/budget.ts`, `import "server-only"`)

- 모든 함수의 첫 인자는 `userId`, 여행 접근은 `accessibleTrips(userId)` 를 같은 문 안에 넣는다. uuid 형식이 틀리면 쿼리 없이 `null`/`false`.
- `getTripBudget(userId, tripId)`, `upsertTripBudget(…)`(§5.2 조건 포함, 거절 이유를 돌려준다).
- `listBudgetItems(userId, tripId)` — 일정에 붙은 행은 일정의 날짜·순서 정보와 함께.
- `setScheduleItemAmounts(userId, tripId, scheduleItemId, …)` — `schedule_item_id` 가 **같은 여행**의 일정인지 같은 문에서 확인하고 upsert(`on conflict (schedule_item_id)`). 예상·실제가 모두 비면 지운다.
- `createExtraItem`·`updateExtraItem`·`deleteExtraItem` — 일정 밖 항목. id 와 여행 id 를 함께 묶는다.
- 예산 설정이 없는 여행에는 금액 행을 넣을 수 없다(넣는 문이 `trip_budgets` 를 함께 확인). 넣는 금액의 통화가 그 여행의 예산·현지 통화인지도 같은 문에서 확인한다.

### 5.6 Server Action (`src/app/trips/budget-actions.ts`)

CLAUDE.md 순서: `getCurrentUser()` → 필드별 검증(`budget-input.ts`) → `userId` 로 좁힌 쿼리 → 무효화. 환율 받기(§5.4)는 검증 뒤, 쓰기 전에. 실패 문구는 한국어(`messages.ts` 에 모은다). 남의 것·없는 것은 똑같이 "찾을 수 없어요".

### 5.7 화면

여행 자세히 보기의 일정표 아래(`page.tsx` 의 `예산(#14)` 자리)에 "예산" 칸. 금액 입력은 **모두 이 칸 안에서** 한다. 일정표의 일정 줄·양식은 바꾸지 않는다(반목표: 일정 코드 복잡도). *(Claude 의 판단 — §7 사용자 확인 항목)*

**예산을 아직 안 정했을 때**
```
예산
여행 예산을 정하면 일정마다 예상 비용과 실제 지출을 적을 수 있어요.
[예산 정하기]
```

**설정 양식**(펼침): 총 예산 [   ] [₩ KRW ▾] · 현지 통화 [없음 ▾] · (현지 통화가 있으면) 예정 환율 ¥100 = ₩[ 920 ]. 환율은 현지 통화 1 단위가 예산 통화 1 미만이면 100 단위로 보이고 입력받는다(엔·동 등). 저장값은 늘 "현지 1 = 예산 몇".

**요약**
```
예산                                              [설정]
총 예산                     ₩1,000,000
이대로 가면                 ₩1,172,000   ₩172,000 초과      ← 빨강 / 여유면 초록
  실제 적은 것  ₩552,000 (그 항목들 예상보다 ₩122,000 더 · 계획에 없던 지출 ₩50,000 포함)
  남은 예상     ₩620,000
예상 합계                   ₩1,050,000
```
실제를 하나도 안 적었으면(예산 짜는 중) "이대로 가면" 대신 "예상 합계 ₩1,050,000 · 총 예산보다 ₩50,000 초과"를 맨 위에.

**날짜별 목록**
```
                                   예상          실제
여행 전체                      ₩420,000      ₩420,000
  항공권 왕복                  ₩420,000      ₩420,000
  + 항목 추가
1일차 · 11월 21일 (금)          ₩82,000       ₩95,600
  오사카성                       ¥1,200        ¥1,200 (≈₩11,040)
  저녁 이자카야                  ¥5,000        ¥6,800 (≈₩62,560 · 11/21 기준환율)
  도톤보리 산책                  —             —
  편의점 간식 (일정 밖)           —             ¥900
  + 항목 추가
2일차 …
여행 기간 밖 (있을 때만)
```
- 날마다 그날 일정을 일정표와 같은 순서(`compareScheduleItems`)로 모두 보이고, 금액이 없는 일정은 "—". 그 아래 일정 밖 항목(만든 순서).
- 줄을 누르면 그 자리에서 양식이 열린다: 예상 [금액] [통화] · 실제 [금액] [통화] · (실제가 현지 통화면) 결제일 [날짜, 기본값 그 일정 날짜·없으면 오늘] · 환율 [빈칸 = "결제일 기준환율로 자동"]. 일정 밖 항목은 이름·날짜(여행 전체 포함) 칸과 지우기가 더 있다.
- 통화 고르기는 예산 통화와 현지 통화 둘 중 하나(현지 통화가 없으면 고르기 없음). 새 금액의 기본값은 현지 통화가 있으면 현지 통화.
- 환율이 예정 환율로 들어갔으면(`planned`) "예정 환율" 표시, 직접 넣었으면 "직접 넣은 환율".
- 휴대폰 너비: 금액 두 칸을 이름 아래 줄로 내린다.
- 일정을 고치면(날짜 이동·지우기) 예산 칸도 같은 무효화로 다시 그려진다.
