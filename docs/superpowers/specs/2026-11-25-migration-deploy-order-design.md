# 마이그레이션과 배포 순서 판정 (#107)

## 왜

`CLAUDE.md` '마이그레이션 PR' 은 순서를 하나만 말한다(적용 → 머지 = DB 먼저). 배포는 순간에 바뀌지 않아 옛 코드가 새 DB 에서 도는 때가 있고, 그때 안전한지는 변경마다 다르다. #89(0008)에서 색인 교체가 옛 코드의 금액 저장을 몇 분 깼고(예측해 받아들임), 롤백하면 남의 내 돈 지출이 보이는 보안 문제가 생겼다. 앞으로 할 #100(칸 추가)·#104(권한 칸 추가) 전에 규칙을 보완한다. #104 도 롤백하면 옛 코드가 권한 칸을 몰라 "보기만" 인 사람이 다시 고칠 수 있게 된다.

## 목표 · 하지 않는 것

- 목표: 마이그레이션 PR 마다 "옛 코드 + 새 DB" 가 깨지는지 두 창에서 판정하고, 안전하지 않으면 무엇을 받아들이는지 또는 어떻게 나누는지 적게 한다. 롤백하면 안 되는 마이그레이션을 다음 세션이 알게 한다.
- 하지 않는 것: 변경 종류별 절차표, 여러 단계 이전(새 칸 추가 → 둘 다 쓰기 → …)의 표준 절차. 아직 한 번도 없던 경우를 미리 규칙으로 쓰지 않는다. 새 문서·스크립트·CI 검사도 만들지 않는다.

## 접근

- **(가) 판정만 적기 — 고름.** PR 본문에 두 창 각각 판정, 안전하지 않으면 감수할 위험을 적거나 PR 을 나눔, 뜻을 바꾸는 마이그레이션 뒤에는 롤백 대신 앞으로 고침. 몇 줄이면 되고 사용자 적고 배포 창이 몇 분인 지금 규모에 맞다.
- (나) 종류별 절차표: 더 정확하지만 없던 경우(삭제·이름 바꾸기)까지 미리 규칙으로 만든다. 고르지 않음.

## 판정의 두 창

1. **적용부터 새 배포 READY 까지**(몇 분). 비어도 되는 칸·새 테이블은 대개 안전. 기본값 없는 NOT NULL 칸, 색인·제약 교체는 옛 쿼리를 깰 수 있다.
2. **그 뒤 옛 배포로 되돌릴 때**(Instant Rollback, 머지 커밋 revert). 새 모양 데이터가 쌓인 뒤라 칸 추가도 위험할 수 있다(0004 제목 없는 일정, 0008 `owner_user_id`). revert PR 도 옛 코드 + 새 DB 라 롤백과 같다.

## 칸·테이블 삭제(코드 먼저)

Drizzle 은 SELECT·INSERT 에 스키마의 칸 이름을 적으므로, `schema.ts` 에서 칸을 지운 새 코드는 칸이 남은 DB 에서도 돈다. 그래서 PR 을 나누지 않고 같은 PR 에서 순서만 바꾼다: `human-approved` → 머지 → 배포 READY 확인 → 적용(실행 직전 사람 확인). 예외: 기본값 없는 NOT NULL 칸은 새 코드의 INSERT 가 그 칸을 빼서 깨지므로, NOT NULL 을 푸는 마이그레이션을 먼저 따로 넣는다. 파괴적 마이그레이션이므로 '규칙' 의 "PR 을 열기 전에 멈추고 보고" 는 그대로다.

## 바꾸는 것

`CLAUDE.md` '마이그레이션 PR' 을 아래로 바꾼다.

```markdown
**마이그레이션 PR.** 자동 머지를 켜지 않는다. 사람이 SQL 을 보고 `human-approved` 라벨을 붙이면 `npm run db:migrate` 를 실행하고(실행 직전 사람 확인), 적용이 성공하면 자동 머지를 켠다(검사가 이미 다 통과했으면 바로 squash 머지). 적용 뒤 PR 을 포기하게 되면 되돌리는 방법을 보고한다.
- 배포는 순간에 바뀌지 않아 옛 코드가 새 DB 에서 도는 때가 두 번 있다. PR 본문 "옛 코드와 새 DB" 에 둘 다 판정한다(안전 / 깨짐: 무엇이 얼마나 / 보안·데이터 손상).
  1. 적용부터 새 배포 READY 까지(몇 분). 비어도 되는 칸·새 테이블은 대개 안전하고, 기본값 없는 NOT NULL 칸이나 색인·제약 교체는 옛 쿼리를 깰 수 있다(#89 `ON CONFLICT`).
  2. 그 뒤 옛 배포로 되돌릴 때(Instant Rollback, 머지 커밋 revert). 새 모양 데이터가 쌓인 뒤라 칸 추가도 위험하다. 옛 코드가 새 칸을 모르고 지나치면 그 칸이 막던 것이 풀린다(#89 `owner_user_id`).
- 1이 깨지면 받아들일 위험을 적는다. 보안·데이터 손상이면 받아들이지 않고 PR 을 나눈다.
- 칸·테이블 삭제는 코드 먼저: `human-approved` → 머지 → 배포 READY 확인 → 적용. Drizzle 은 쿼리에 스키마의 칸 이름을 적어 `schema.ts` 에서 지운 코드는 칸이 남은 DB 에서도 돈다. 기본값 없는 NOT NULL 칸은 NOT NULL 을 푸는 마이그레이션부터 따로 넣는다.
- 2가 보안·데이터 손상이면 그 배포 앞으로는 되돌리지 않고 앞으로 고친다. `docs/status.md` '알아 둘 것' 의 "롤백 금지선" 에 적는다.
```

`docs/status.md` '알아 둘 것' 의 "마이그레이션과 배포 사이" 줄(내용이 위 규칙으로 옮겨감)을 아래로 바꾼다.

```markdown
- **롤백 금지선**(`CLAUDE.md` '마이그레이션 PR'): 아래 배포보다 앞의 배포로 Instant Rollback·revert 하지 않고 앞으로 고친다.
  - 마이그레이션 0008(#89, 머지 커밋 `7ff21c0`): 옛 코드가 `budget_items.owner_user_id` 를 몰라 남의 내 돈 지출이 모두에게 보인다.
```

## 빌더에게 남긴 것

- 문장 다듬기(뜻은 위와 같게). `CLAUDE.md` 는 위험 경로라 PR 에 `human-approved` 가 필요하고 마이그레이션은 없다.
- 금지선이 0008 이면 그 앞(0000–0007)은 따로 볼 필요가 없고 0009 만 남는다. 0009 를 2번 창에서 판정: 옛 코드는 `for_user_id` 를 몰라 나만 일정이 모두의 일정처럼 동선에 들어가지만, 나만 일정은 원래 남에게도 접힌 줄로 보이므로 보안 문제는 아니다(깨짐: 동선이 사람별이 아니게 됨). 그래서 금지선은 0008 하나. PR 에서 근거를 다시 확인한다.

## 구현 중 바뀐 것(`/code-review`)

- 삭제(코드 먼저)는 1번 창을 "머지부터 적용까지 새 코드 + 옛 DB" 로 판정한다.
- 머지 뒤 적용 전에 세션이 끝나면 `docs/status.md` '남은 확인' 에 "적용 안 된 마이그레이션" 을 적고, 다음 마이그레이션 PR 본문에도 그 SQL 을 적는다(다음 `db:migrate` 가 함께 적용).
- 추가와 삭제가 섞인 마이그레이션은 늘 PR 을 나눈다.
- 마이그레이션 PR 의 머지 커밋은 revert 하지 않는다(마이그레이션 파일·journal 만 사라져 DB 와 어긋남). 되돌릴 것은 새 마이그레이션으로.
- "앞으로 고친다" 는 "고친 코드를 새로 배포한다" 로(“앞으로” 가 두 뜻으로 읽힘).
