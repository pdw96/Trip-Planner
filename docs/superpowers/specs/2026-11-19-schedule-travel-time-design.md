# 일정표에 일정 사이 예상 이동 시간 보이기 (#37)

2026-11-19. 사용자 승인.

## 1. 왜

#35 설계 대화에서 나온 사용자 생각.

- 시각이 확정된 일정(예약한 교통편, 식당 예약)이 있고, 나머지는 시각이 가변적이다.
- 가변 일정은 시각을 직접 적기보다 **일정 사이 예상 이동 시간**으로 보고 싶다.
- 시각을 자동으로 계산해 채우는 것은 원하지 않는다.

지금 이동 시간은 지도 칸의 N일차 탭에서만 보인다. 일정표를 훑으면서 "다음 장소까지 얼마나 걸리나"를 바로 보게 한다.

## 2. 목표 · 비목표 · 반목표

- 목표
  - 일정표의 각 날에서, 장소가 이어진 일정 사이에 예상 이동 시간 한 줄("🚇 32분 · 2호선")을 보인다. 기준점(숙소)에서 첫 장소, 마지막 장소에서 기준점 구간도 보인다.
  - 버튼을 누르지 않아도, 화면에 들어온 날만 자동으로 묻는다.
- 비목표 (사용자 결정)
  - 예상 도착 시각, 확정 일정 앞 여유, "늦을 수 있음" 표시. 머무는 시간 입력. (사용자가 고른 1번: 이동 시간만)
  - "확정 일정"을 따로 표시하는 칸. 지금의 시각 칸 그대로 둔다.
  - 일정 순서를 직접 바꾸기 → #41. 그때까지 순서는 지금 정렬(시각 순, 시각 없음은 뒤) 그대로다.
  - 시각 자동 계산·채우기.
  - 자가용 이동 시간(Routes 한계, #13).
- 반목표 (기술적으로 돌아가도 실패인 것)
  - 일정표를 열기만 해도 모든 날의 구간을 한꺼번에 묻는다.
  - 지도 칸 N일차 탭과 일정표가 같은 날을 따로 두 번 묻는다.
  - 이동 시간을 기다리거나 실패해서 일정 줄 읽기·고치기·완료 체크가 막히거나 늦어진다.
  - 일정을 고친 뒤에도 이전 동선의 이동 시간이 남아 있다(다른 장소 사이 시간이 보인다).
  - 경로 정보를 DB 나 요청을 넘어서는 서버 메모리에 저장한다.

## 3. 제약

- Google 약관(#13 설계 §3.2): 경로 정보는 저장하지 않는다. 브라우저 화면 상태로만 둔다(지금 N일차 탭과 같다).
- 이동 정보는 Route Handler `GET /trips/[id]/day-route?date=` 로만 묻는다. Server Action 으로 묻지 않는다(Server Action 은 하나씩 차례로 보내져 저장이 Google 응답을 기다린다, #13). 인자는 여행 id 와 날짜뿐이다(서버가 그 사용자의 장소로만 구간을 만든다).
- 비용: 하루 한 번 묻는 데 길찾기(Routes) 호출이 구간 수만큼(대중교통, 필요하면 도보), 장소 정보(나라·시간대) 호출이 장소 수만큼 든다. 하루 구간 상한 20(`MAX_LEGS_PER_DAY`)은 그대로.
- Next 16 Activity: 지나온 화면은 `display:none` 으로 보관된다. 숨은 화면에서는 묻지 않는다.
- 단위 시험 대상 순수 모듈(`src/lib/day-route.ts` 등)은 다른 모듈을 import 하지 않는다.

## 4. 방법

### 4.1 고려한 방법 (사용자가 B 를 고름)

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| A | 날마다 "이동 시간 보기" 버튼 | 호출이 가장 적다 | 훑어보려면 날마다 눌러야 한다 — 목적과 어긋남 |
| **B** | **화면에 들어온 날만 자동으로 묻기, 결과는 지도 탭과 함께 씀** | 누르지 않고 보인다. 같은 날은 한 번만 묻는다 | 끝까지 스크롤하면 날 수만큼 묻는다(지금 한도 안) |
| C | 지도 칸에서 연 N일차 탭의 날만 일정표에도 | 새 호출 없음 | 지도 탭과 일정표의 관계가 드러나지 않는다 |

### 4.2 화면

일정 줄 사이, 도착하는 일정 줄 바로 위에 이동 줄 하나. 시각 칸 자리는 비우고 작은 회색 글씨.

```
1일차 · 12월 3일 (목)
        ↓ ○○호텔에서 · 🚇 25분 · 2호선           길찾기 ↗
09:30  경복궁
       점심 자유 (장소 없음)
        ↓ 경복궁에서 · 🚇 18분 · 3호선           길찾기 ↗
18:00  ○○식당
        ↓ ○○호텔까지 · 🚌 30분                   길찾기 ↗
 + 일정 추가
 ⓘ 국내에서는 대중교통 길찾기만 돼요. …
```

- **자리**: 구간의 도착 일정 줄 바로 위. 도착이 일정이 아닌 구간(마지막 장소 → 기준점)은 그날 마지막 일정 줄 아래(+ 일정 추가 위).
  - 기준점과 같은 장소의 일정이 그날 처음이나 끝에 있으면(예: 마지막 일정 "18:00 호텔 체크인") 기준점과 한 점으로 합쳐진다. 그 점의 구간은 **일정 id 를 우선**한다(내 판단): 체크인 일정 줄 위에 "○○식당 → 호텔" 구간이 오고, 그 아래 돌아가는 구간은 따로 없다. 일정이 없는 기준점만 null 이다.
- **출발지 이름**: 출발이 기준점이면 "<기준점 이름표>에서", 도착이 기준점이면 "<기준점 이름표>까지"(내 판단: 기준점이 숙소 종류가 아닐 수도 있어 고정 문구 "숙소"보다 이름표가 정확하다). 출발 일정과 도착 일정 사이에 다른 줄(장소 없는 일정, 좌표 없는 장소의 일정)이 끼어 있으면 "○○에서"로 출발 장소 이름표를 붙인다. 바로 앞 줄이 출발 일정이면 출발지를 적지 않는다.
- **글자**: 지금 `legText` 그대로("🚇 32분 · 2호선 · 환승 1회", "🚶 12분 (대중교통 정보 없음)"). 결과가 직선(한국 짧은 구간 등, 글자가 빈 값)이면 "직선 1.2km". 기다리는 중이면 "이동 시간 불러오는 중…". 실패면 "이동 정보를 불러오지 못했어요" + "다시" 버튼.
- **길찾기 ↗**: 지금 N일차 탭과 같은 Google 길찾기 링크(새 탭).
- **안내 문구**(국내·일본·그 밖): 그날 결과에 있으면 그날 일정 줄 아래(+ 일정 추가 바로 위)에 지금 N일차 탭과 같은 문구.
- 구간이 없는 날(좌표 있는 장소가 이어진 일정이 없음)은 이동 줄도, 요청도 없다.
- 같은 장소가 연달아 오면 한 점으로 합친다(지금 동선 규칙). 그 사이에는 이동 줄이 없다.
- 여행 기간 밖 일정 모음에는 이동 줄을 보이지 않는다.
- 고치기 입력칸이 열린 줄 위의 이동 줄은 그대로 둔다.

### 4.3 언제 묻나

- 날 칸(`section#day-<날짜>`)이 화면에 들어와 **약 0.5초 머물면** 그날을 묻는다(빠르게 스크롤해 지나간 날은 묻지 않는다). IntersectionObserver, 화면 위아래로 조금 여유.
- 그날 동선이 바뀌면(일정의 장소·시각·날짜, 기준점, 장소 좌표가 바뀌어 서버가 새로 그림) 다시 묻는다. 화면에 있으면 바로, 아니면 다시 들어올 때.
- 같은 날·같은 동선의 결과는 그 화면에 있는 동안 다시 묻지 않는다. 화면을 떠났다 돌아와도(Activity) 남아 있으면 다시 묻지 않는다. 새로 고침하면 새로 묻는다(저장하지 않으므로).
- 화면을 벗어난 날의 진행 중인 요청은 끊지 않는다(이미 Google 을 불렀으니 결과를 받아 둔다). 페이지를 떠나면 끊는다.

### 4.4 지도 탭과 결과 함께 쓰기

- 지금 `trip-map-panel.tsx` 의 `useDayRoute`(요청·늦은 응답 버리기·끊기)를 페이지 단위 클라이언트 저장소로 옮긴다. 이름은 구현 때 정한다(예: `DayRouteProvider` + `useDayRoute(date, signature, enabled)`).
- 저장소는 `page.tsx` 에서 지도 칸과 일정 칸을 함께 감싼다. 키는 `날짜 + 동선 서명`. 지도 탭이 이미 받은 날을 일정표가 보면 다시 묻지 않고, 그 반대도 같다.
- 동선 서명은 지금 `routeSignature`(기준점 id + 구간마다 `from>to@timing`)를 공용 함수로 옮겨 두 칸이 같은 함수로 만든다.
- 지도 탭의 지금 동작은 바꾸지 않는다: N일차 탭을 열면 묻고, 같은 탭을 다시 누르면 다시 묻는다. 탭을 바꿔도 진행 중 요청은 끊지 않는다(구현 때 결정: 끊어도 서버의 Google 호출은 멈추지 않으므로(#13 남은 지적) 받아 두는 편이 낫다). 페이지를 떠나면(Activity 로 숨음 포함) 기다리던 요청만 끊고, 받은 결과는 남긴다.

### 4.5 서버 쪽

- `buildDayRoute` 의 stop 에 일정 id 를 싣는다(`DayStop.itemId`). 합친 점은 처음 일정 id(도착 쪽)와 마지막 일정 id(출발 쪽)를 갖고, 구간마다 `fromItemId`·`toItemId` 를 낸다. 기준점과 일정이 합쳐진 점은 일정 id, 일정 없이 기준점만인 점은 null(§4.2). 지도 칸은 쓰지 않아도 된다.
- 일정 칸(`schedule-section.tsx`)은 그날 동선 뼈대를 직접 만든다. 지금 지도 칸(`map-section.tsx`)과 같은 규칙이므로, 날짜별 뼈대(구간·서명·일정 id)를 만드는 서버 함수를 하나로 모아 두 칸이 같이 쓴다. 일정 칸에 `listTripBases` 조회가 하나 늘어난다(이미 `userId` 범위).
- `loadDayRoute` 응답의 구간(`LegView`)에 `fromItemId`·`toItemId` 를 더한다(필드 추가만, 지도 칸은 그대로 쓴다). 일정표는 **응답의 일정 id 로** 이동 줄 자리를 정한다. 뼈대는 답이 오기 전 "불러오는 중…" 줄의 자리와 저장소 키(서명)에만 쓴다. 그래서 두 칸이 읽은 값이 달라도 이동 줄이 엉뚱한 자리에 붙지 않는다.
- 알려진 작은 빈틈(내 판단, 받아들임): 지도 칸은 30일 지난 좌표를 새로 고치며 따로 기다리고, 일정 칸은 먼저 그린다. 그 사이 장소가 좌표를 얻거나 잃으면 그 페이지 보기 동안 두 칸의 서명이 달라 같은 날을 한 번 더 물을 수 있다. 장소마다 30일에 한 번, 좌표 갱신이 실패하거나 처음 성공하는 페이지 보기에서만 생기므로 일정 칸이 지도를 기다리게(일정이 늦게 보이게) 바꾸지 않는다.

## 5. 시험

- 단위(`node --test`): `buildDayRoute` 의 `fromItemId`·`toItemId`(기준점, 기준점과 같은 장소의 첫·끝 일정, 같은 장소 합치기, 좌표 없는 장소 건너뛰기), 이동 줄 자리·출발지 문구를 정하는 순수 함수(있다면).
- 브라우저(Playwright, 로컬 dev + 테스트 계정): 여러 날 여행에서 스크롤해 화면에 들어온 날만 `day-route` 요청이 나가는지, 지도 N일차 탭을 연 날은 일정표에서 다시 묻지 않는지, 일정의 장소를 바꾸면 그날만 다시 묻는지, 장소 없는 일정이 끼었을 때 "○○에서" 문구, 휴대폰 너비 줄 바꿈.
- 서버 쪽 소유권: 새 Route Handler·Server Action 이 없다. 일정 칸에 늘어나는 조회(`listTripBases`)는 이미 `userId` 범위다.
