# 여행별 날짜 일정표 설계

- 날짜: 2026-11-18
- 이슈: pdw96/Trip-Planner#12
- 상태: 승인됨 (2026-11-18). "Claude 판단" 표시 항목도 이 승인에 포함된다. 장소 링크를 여는 방식(§5.1)은 구현 뒤 브라우저 확인에서 사용자가 "새 탭 유지"로 정했다.

## 1. 의도

여행 하나 안에 날짜별 일정(1일차 09:30 공항, 15:00 숙소 체크인 …)을 적고 보게 한다. 사용자는 본인과 지인 2명이고 한국어를 쓴다.

쓰는 상황은 두 가지가 비슷한 비중이다 (사용자 답).
- 여행 전: 컴퓨터나 휴대폰으로 일정을 짜고 다듬는다. 전체를 한눈에 보는 것이 중요하다.
- 여행 중: 휴대폰으로 "오늘 뭐 하지"를 보고, 한 일을 체크하고, 그 자리에서 고친다.

장소는 지금은 글자로만 적는다. 지도 연동(장소 검색, 좌표, 동선)은 사용자가 원하지만 #13(가 볼 장소)에서 장소 목록과 함께 설계하고, 그때 일정이 장소를 고를 수 있게 잇는다 (사용자 결정).

## 2. 목표 / 비목표 / 반목표

**목표**
- 여행 자세히 보기(`/trips/[id]`) 아래에 여행 기간의 모든 날을 1일차부터 차례로 보인다. 일정이 없는 날도 보인다.
- 일정 추가·고치기·삭제, 완료 체크.
- 일정 하나: 시각(선택), 제목(필수), 장소(선택, 글자), 메모(선택), 완료 여부.
- 여행 중이면 오늘 날짜에 "오늘" 표시와 그날로 가는 링크.
- 여행 날짜를 줄여도 일정은 사라지지 않는다.

**비목표**
- 지도 연동·좌표·동선 (#13 이후).
- 여러 날에 걸친 일정(예: 숙소 3박), 끝 시각, 반복 일정.
- 끌어서 순서 바꾸기. 순서는 시각으로 정한다.
- 공유·함께 고치기 (#15). 단 접근 확인은 #15 가 한 곳만 바꾸도록 만든다(§5.4).
- 새 의존성(`package.json` 변경).

**반목표 (동작해도 실패로 본다)**
- 남의 여행이나 남의 일정 id 로 읽기·쓰기가 되는 것. 또는 "없음"과 다른 반응으로 그 id 가 있다는 것이 드러나는 것.
- 일정 id 와 여행 id 를 따로 믿는 것. 예: 내 여행 id 와 남의 일정 id 를 함께 보내 남의 일정이 고쳐지는 것.
- 여행 날짜를 고쳤다고 일정이 지워지거나 보이지 않게 되는 것.
- 검증 오류가 났는데 사용자가 적은 내용이 사라지는 것.
- "오늘"이 한국 날짜와 하루 어긋나는 것.
- 완료 체크가 눌렀는데 반응이 늦어 두 번 누르게 되는 것.

- DB 드라이버는 neon-http 라 대화형 트랜잭션이 없다. 소유권 확인은 한 SQL 문 안의 조건으로 한다(§5.4).
- `src/lib/*.ts` 의 순수 모듈은 다른 모듈을 import 하지 않는다(`node --test` 로 시험).

## 4. 고려한 방식

| 방식 | 내용 | 판단 |
|---|---|---|
| **A. 일정 테이블 하나** | `schedule_items` 에 여행 id·날짜·시각·제목·장소·메모·완료. 날짜 칸은 여행 기간에서 만들고, 기간 밖 일정은 날짜 비교로 골라낸다. | **선택 (사용자).** 가장 단순하다. 날짜를 줄여도 행은 그대로라 "기간 밖" 표시가 쉽다. 공유(#15)·장소 연결(#13)은 조건 변경·컬럼 추가로 받는다. |
| B. 날(day) 테이블 + 일정 테이블 | `trip_days` 를 두고 일정이 그 날에 매달린다. | 여행 날짜를 고칠 때마다 날 행을 맞춰야 해 복잡하고 어긋나기 쉽다. 날마다 메모를 달 수 있다는 이점은 지금 요구에 없다. |
| C. 여행에 JSON 으로 저장 | `trips` 에 일정 목록 JSON 칸 하나. | 검사 제약을 못 걸고, 두 사람이 동시에 고치면(#15) 한쪽이 덮어씌워진다. |

입력 방식은 두 가지를 견줬다. (a) 그 자리에서 입력칸이 펼쳐짐, (b) 별도 화면으로 이동. 사용자가 (a)를 골랐다. 여러 개를 연달아 적기 쉽고 휴대폰에서 위치를 잃지 않는다.

보기 방식은 (a) 모든 날을 세로로 이어서, (b) 날짜 탭 중 사용자가 (a)를 골랐다.

## 5. 정한 것

### 5.1 화면 (사용자 승인)

여행 자세히 보기의 기존 머리(이름·여행지·날짜·메모) 아래에 "일정" 칸이 붙는다.

```
일정                                  [오늘 일정으로 ↓]

1일차 · 12월 3일 (목)
  09:30  인천공항 출발                       ☐
         📍 인천국제공항 제1터미널
  15:00  호텔 체크인                         ☐
         예약번호 AB1234
         저녁 시장 구경                       ☐
  + 일정 추가

2일차 · 12월 4일 (금)  [오늘]
  10:00  박물관                (흐리게, 줄)   ☑
  + 일정 추가

3일차 · 12월 5일 (토)
  아직 일정이 없어요
  + 일정 추가

여행 기간 밖 일정
  12월 6일 (일)
    11:00  귀국 비행기                       ☐
```

- 날 제목: `N일차 · M월 D일 (요일)`. 연도가 바뀌는 여행이면(12/30–1/2) 각 날짜에 연도를 붙일지는 구현자가 정한다.
- 일정 줄: 시각(없으면 비움), 제목, 완료 체크. 장소와 메모가 있으면 제목 아래에 작게. 메모는 줄바꿈을 살린다.
- 완료된 일정은 흐리게(제목 취소선).
- **오늘**: 오늘(한국 날짜, `todayInSeoul()`)이 여행 기간 안이면 그날 제목에 "오늘" 표시를 붙이고, 일정 칸 위에 그날로 가는 링크(`#day-YYYY-MM-DD` 앵커)를 둔다. 자동으로 스크롤하지는 않는다. (Claude 판단: 전체를 짜는 용도와 부딪히지 않게)
- **여행 기간 밖 일정**: 날짜가 여행 시작 전이거나 끝 뒤인 일정이 있으면 맨 아래에 이 칸을 보인다. 날짜순으로 묶어 `M월 D일 (요일)`(필요하면 연도) 제목 아래에 같은 줄 모양으로. 없으면 칸을 감춘다.
- 장소를 누르면 새 탭에서 Google 지도 검색이 열린다: `https://www.google.com/maps/search/?api=1&query=<장소 인코딩>`. API 키가 필요 없고 해외 여행지도 찾는다. 팝업 창이 아니라 일반 링크(`target="_blank"`, `rel="noopener noreferrer"`)이고, 휴대폰에서는 대개 Google 지도 앱이 열린다. (Claude 판단, 브라우저 확인 뒤 사용자가 새 탭 유지로 확정)

### 5.2 순서 (사용자 승인 + Claude 판단)

하루 안에서: 시각 있는 일정이 시각 순으로 먼저, 시각 없는 일정은 그날 맨 아래(Claude 판단). 같은 시각끼리·시각 없는 것끼리는 만든 순서(`created_at`, 같으면 `id`).

### 5.3 추가·고치기·완료·삭제 (사용자 승인 + Claude 판단)

- **추가**: 그날의 "+ 일정 추가"를 누르면 그 자리에 입력칸(시각, 제목, 장소, 메모)이 펼쳐진다. 날짜는 누른 날로 정해진다. 저장하면 목록에 들어가고, 입력칸은 비운 채 열린 상태로 남아 다음 일정을 바로 적을 수 있다. "닫기"로 접는다. (연달아 적기 — Claude 판단)
- **고치기**: 일정 줄을 누르면(또는 줄의 "고치기") 그 자리에서 같은 입력칸이 기존 값으로 펼쳐지고, 날짜 고르기가 더해진다. 날짜 목록은 여행 기간의 날들(`N일차 · M월 D일`)이고, 기간 밖 일정이면 그 일정의 지금 날짜도 목록에 들어간다. 저장하면 접힌다. "취소"는 바꾸지 않고 접는다.
- **한 번에 하나**: 입력칸은 화면 전체에서 하나만 열린다. 다른 것을 열면 앞의 것은 저장 없이 접힌다. (Claude 판단: 휴대폰에서 어느 것을 고치는지 헷갈리지 않게)
- **완료 체크**: 누르면 바로 화면에 반영되고(낙관적 갱신) 서버에 저장한다. 실패하면 되돌리고 "저장하지 못했어요. 잠시 후 다시 시도해 주세요."를 짧게 보인다. 입력칸을 열지 않고 줄에서 바로 누른다. (Claude 판단)
- **삭제**: 고치기 입력칸 안의 "삭제" → "이 일정을 삭제할까요?" 확인 창(`window.confirm`, 여행 삭제와 같은 방식) → 지운다. (Claude 판단)
- 화면을 떠났다 돌아오면(Next 의 Activity 보관) 열려 있던 입력칸과 지난 오류는 사라져 있어야 한다. `trip-form.tsx` 의 key 재설정 방식을 참고한다.

### 5.4 데이터와 접근 확인 (사용자 승인: A안 / 세부는 Claude 판단)

**테이블 `schedule_items`**

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `id` | `uuid` PK, `defaultRandom()` | |
| `trip_id` | `uuid` not null, FK → `trips.id` `on delete cascade` | 여행을 지우면 일정도 지워진다 |
| `date` | `date` not null | 여행 기간 검사 제약은 걸지 않는다(날짜를 줄여도 남겨야 하므로) |
| `time` | `time` null | 분 단위로만 저장(`HH:MM`, 초는 0) |
| `title` | `text` not null | |
| `place` | `text` null | |
| `memo` | `text` null | |
| `done` | `boolean` not null default `false` | |
| `created_at` / `updated_at` | `timestamptz` not null default now, `updated_at` 은 `$onUpdate` | `trips` 와 같은 방식 |

- 인덱스: `(trip_id, date)`.
- 마이그레이션은 `CREATE TABLE` + FK + 인덱스뿐이라 파괴적이지 않다. `npm run db:generate` 로 만들고 손대지 않는다.
- #13 에서 장소를 이을 때는 `place_id` 같은 null 허용 컬럼을 더하는 비파괴 변경이 될 것이다(이번에 만들지 않음).

**쿼리 `src/db/queries/schedule-items.ts`** (`import "server-only"`, 모든 함수 첫 인자 `userId`)

- 여행 접근 조건은 `src/db/queries/trips.ts` 의 `accessibleTrips(userId)` 하나만 쓴다(지금은 내보내지 않으므로 내보낸다). 공유(#15)는 이 조건만 바꾸면 일정도 따라온다.
- 목록 `listScheduleItems(userId, tripId)`: 여행 접근 조건을 통과한 여행의 일정만, §5.2 순서로.
- 추가: 액션에서 먼저 `getTrip(userId, tripId)` 로 여행을 확인하고(여행 기간도 여기서 얻는다) 넣는다. 그 사이 여행이 지워지면 FK 오류 → 저장 실패 문구.
- 고치기·완료·삭제: **한 SQL 문**의 `where` 에 `schedule_items.id = itemId` **그리고** `schedule_items.trip_id = tripId` **그리고** `trip_id in (접근 가능한 여행)` 을 함께 건다. 바뀐 행이 없으면 "찾을 수 없음". 여행 id·일정 id 는 uuid 형식이 틀리면 쿼리 없이 "찾을 수 없음".
- 고치기에서 날짜 규칙(§5.5)이 "원래 날짜 그대로"를 허용하므로, 그 비교도 같은 문의 조건으로 넣거나 같은 범위 조건으로 먼저 읽는다. 방법은 구현자가 정하되, 다른 사람의 일정 날짜가 드러나지 않아야 한다.

**Server Action** (`src/app/trips/` 아래, 파일 위치는 구현자)

- 추가(`tripId`·`date` bind), 고치기(`tripId`·`itemId` bind), 완료 전환(`tripId`·`itemId`·`done`), 삭제(`tripId`·`itemId`).
- 순서: `getCurrentUser()`(없으면 `redirect("/")`) → 필드별 입력 검증 → `userId` 로 범위를 좁힌 쿼리 → `revalidatePath("/trips/<id>")`. bind 값도 클라이언트가 바꿀 수 있는 값으로 보고 쿼리 조건으로 막는다.
- 여행이나 일정을 찾을 수 없으면 `notFound()` (남의 것과 없는 것 같은 반응, CLAUDE.md). 단 완료 전환은 줄에서 바로 부르는 낙관적 갱신이라, 대상 없음과 저장 실패를 똑같이 실패로 돌려주고 화면은 되돌린 뒤 같은 실패 문구를 보인다(반응이 같으므로 남의 일정이 있는지 드러나지 않는다). (Claude 판단)
- 추가·고치기는 `useActionState` 로 필드 오류와 입력값을 돌려준다(#11 양식과 같은 모양).

### 5.5 필드와 검증 (한도는 Claude 판단)

| 필드 | 필수 | 규칙 |
|---|---|---|
| 시각 `time` | 아니오 | 비면 `null`. 있으면 `HH:MM`, 00:00–23:59 |
| 제목 `title` | 예 | 앞뒤 공백 제거 뒤 1–100자 |
| 장소 `place` | 아니오 | 앞뒤 공백 제거 뒤 200자 이하, 비면 `null` |
| 메모 `memo` | 아니오 | 앞뒤 공백 제거 뒤 2000자 이하, 비면 `null` |
| 날짜 `date` (고치기만) | 예 | 실제 있는 `YYYY-MM-DD`. 여행 기간 안이거나, 이 일정의 원래 날짜 그대로 |

- 추가의 날짜도 bind 값이므로 서버에서 같은 규칙(여행 기간 안)을 검사한다.
- 글자 수는 코드 포인트 기준(`trip-input.ts` 와 같음). 검증은 순수 함수(`src/lib/schedule-input.ts` 등)로 두고 `node --test` 시험을 붙인다. `isValidIsoDate` 등 중복은 구현자가 정리하되 순수 모듈 규칙을 지킨다.
- 시각 칸은 `<input type="time">`(휴대폰 기본 시각 고르기). 브라우저 검증에 기대지 않는다.
- 오류 문구 예: "제목을 입력해 주세요.", "시각을 올바르게 입력해 주세요.", "여행 기간 안의 날짜를 골라 주세요.", 저장 실패는 "저장하지 못했어요. 잠시 후 다시 시도해 주세요."

### 5.6 화면 구조 (Claude 판단)

- 일정 칸은 Server Component 가 그린다. `TripDetail` 의 같은 `<Suspense>` 안에서 `getTrip` 뒤에 일정을 읽는다(여행과 일정이 함께 나타남).
- 날짜 칸 만들기·일정 묶기(기간 안 날짜별, 기간 밖)·정렬·요일 표시는 순수 함수(`src/lib/` 아래)로 두고 시험한다. 날짜는 #11 처럼 `"YYYY-MM-DD"` 문자열로 다룬다(Date 로 바꾸면 시간대가 끼어든다).
- Client Component 는 말단만: 일정 줄(완료 체크, 펼치기), 입력칸 양식, "한 번에 하나"를 위한 열림 상태를 쥔 작은 컨테이너. 열림 상태를 어디에 둘지는 구현자.
- 일정 수는 여행당 수십 개 수준으로 본다. 페이지 나누기 없음.

### 5.7 확인 순서

1. 순수 함수 시험(`node --test 'src/**/*.test.mjs'`), `npm run lint`, `npm run typecheck`, `npm run build`.
2. 마이그레이션 PR 을 연다. 본문 맨 위 "사람 확인 필요"(위험 경로: `src/db/schema.ts`, `drizzle/**`)와 SQL 전문, 파괴적 여부 판정(비파괴).
3. 사람이 `human-approved` 를 붙이면 `npm run db:migrate`(실행 직전 사람 확인).
4. 그 뒤 브라우저 확인: `docs/status.md` '알아 둘 것'의 임시 테스트 계정 방식(넣기·지우기 전 SQL 전문을 보이고 각각 확인). 사용자 A·B 를 넣고 확인한다:
   - 추가(연달아 두 개), 시각 없는 일정이 맨 아래, 고치기·날짜 옮기기, 완료 체크, 삭제 확인 창, 검증 오류 때 입력이 남음.
   - 여행 날짜를 줄였을 때 "여행 기간 밖 일정"에 나타나고, 다시 늘리면 제자리로.
   - 오늘 표시(오늘이 기간 안인 여행).
   - A 가 B 의 여행·일정 id 로 고치기·완료·삭제를 시도하면 찾을 수 없음, B 의 일정은 그대로.
   - 휴대폰 폭(예: 390px) 화면.
   - 끝나면 테스트 사용자 행을 지운다(`session`·`trips`·`schedule_items` 는 cascade). 남은 행 0개 확인.
5. 문제가 없으면 자동 머지를 켜고, 배포 뒤 프로덕션에서 화면이 뜨는지 본다.

## 6. 구현자에게 맡기는 것

- 파일 이름·위치의 세부, 컴포넌트 나누기, 열림 상태를 둘 곳.
- 화면 스타일(기존 zinc 계열·둥근 버튼을 따른다), 오늘 표시의 모양, 체크 상자의 모양.
- 연도가 바뀌는 여행의 날짜 표기.
- 오류 문구의 최종 표현.
- 고치기의 "원래 날짜 그대로" 비교를 한 문에 넣을지, 범위 조건으로 먼저 읽을지(§5.4 조건 안에서).
- 완료 전환 실패 문구를 보이는 방식(줄 옆 짧은 문구 등).
